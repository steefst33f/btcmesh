```
lora/
└── btcmesh/
    ├── btcmesh_cli.py         # Client script for sending transactions
    ├── btcmesh_server.py      # Server/Relay script for processing transactions
    ├── core/                  # Core logic for the server/relay
    │   ├── __init__.py
    │   ├── config_loader.py   # For loading config.ini
    │   ├── logger_setup.py    # For setting up consistent logging
    │   ├── transaction_parser.py # For decoding raw Bitcoin transactions
    │   ├── rpc_client.py      # For interacting with Bitcoin RPC
    │   └── reassembler.py     # For reassembling chunked messages
    ├── project/               # Project planning documents (this file, reference_materials.md)
    │   ├── tasks.txt
    │   └── reference_materials.md
    ├── logs/                  # Directory for log files (created at runtime)
    │   └── btcmesh_server.log
    │   └── btcmesh_cli.log    # If btcmesh_cli.py also implements file logging
    ├── tests/                 # Unit and integration tests
    │   ├── __init__.py
    │   ├── test_config_loader.py
    │   ├── test_transaction_parser.py
    │   ├── test_rpc_client.py
```

# EPIC: Bitcoin Transaction Relay over LoRa Meshtastic

**Goal:** To enable users to broadcast Bitcoin raw transactions by sending them as **chunked hexadecimal strings** via a LoRa Meshtastic direct message, using a dedicated client script (`btcmesh-cli.py`). The relay device (`btcmesh-server.py`) will reassemble these chunks, decode, validate, and then relay the complete transaction to a configured Bitcoin RPC node.

**User Persona:** A Bitcoin user who wants to broadcast a raw transaction using a command-line tool (`btcmesh-cli.py`), potentially in an environment with limited or censored internet access, but with LoRa Meshtastic network availability.

## EPIC 5: Device Power-Cycle Recovery (Watchdog)

**Goal:** Automatically recover a Meshtastic USB device that has become unresponsive ("wedged") without requiring a manual physical unplug/replug, by detecting the lockup and power-cycling the device's USB port under software control.

**Background:** Reported in `project/issues.txt` (Issue 12, Issue 16): Meshtastic serial devices occasionally lock up after extended runtime or rapid reconnect cycles, and the only known fix so far is a manual hardware power cycle (unplug, wait 10-15s, replug). This epic automates that recovery using either a uhubctl-compatible USB hub (software-only) or a DIY relay/MOSFET board wired into the device's VBUS line (fallback if the hub isn't compatible), driven by a shared watchdog used by both the client and server.

**Priority:** Medium - addresses a real operational pain point, but requires real-hardware testing to validate the liveness-check and re-enumeration-matching assumptions below.

# EPIC 6: Device Identification in GUI Dropdowns

**Goal:** Show each connected Meshtastic device's node ID alongside its serial port path in both GUIs' device dropdowns, so an operator with multiple devices attached doesn't have to guess or remember which physical device is on which port.

**Background:** Both GUIs' device dropdowns (client GUI's device spinner, server GUI's Story 18.2 device settings spinner) currently list only OS-level port paths (e.g. `/dev/cu.usbserial-0001`), populated by `core/meshtastic_utils.py`'s `scan_meshtastic_devices()`. The node ID is a Meshtastic protocol-level identity, not a USB-level one - getting it requires actually connecting to the device (there's no lighter-weight query), so it's never been surfaced at scan time.

**Priority:** Low - a real usability improvement, not a functional gap.

# EPIC 7: Reliability Hardening from Overnight Field Testing

**Goal:** Fix a critical client GUI freeze found during real overnight operation (Issue 21), and close the observability/detection gaps that let it go unnoticed until it caused a hang requiring a force-kill.

**Background:** Running the client and server GUIs unattended overnight surfaced a real bug: `TransactionSender`'s send path has no timeout around the underlying transport call, so a genuinely wedged device can freeze the entire client GUI with no way to abort out of it. Investigating this also surfaced that neither the client nor the server GUI (only `btcmesh_server_cli.py`) has `DeviceWatchdog` wired in - so an overnight wedge on either could currently go completely undetected. See Issue 21 in `project/issues.txt` and `project/plans/story_28_1.md` for the full design.

**Priority:** High - the send hang is a real, reproduced application freeze requiring a force-kill.

# EPIC 8: Client GUI Background-Operation Feedback

**Goal:** Give the client GUI's brief background connect/probe operations (device scan, identity probing, known-nodes fetch) a real, visible busy indicator - without blocking anything the user could otherwise already do (select an unprobed device, type a destination node ID by hand).

**Background:** Issue 39 (`project/issues.txt`) found that only Send (`_connect_with_retry()`) currently gives clear "in progress" feedback (disabled controls, explicit status). Explicitly a low-priority UX enhancement, not a bug.

**Priority:** Low - nice-to-have, no functional impact.
