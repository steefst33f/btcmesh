## Protocol: Redundant status field in response messages

**Issue 7: Status field carries no information** ✅ RESOLVED (Story 20.4)

The three server→client response message types each contain a status field that is always fixed to the same value:

| Message type | Status field | Always |
|-------------|-------------|--------|
| `BTC_CHUNK_ACK\|<session>\|<chunk>\|OK\|...` | `OK` | Always OK — being an ACK already implies success |
| `BTC_ACK\|<session>\|SUCCESS\|TXID:<txid>` | `SUCCESS` | Always SUCCESS — the ACK prefix already means success |
| `BTC_NACK\|<session>\|ERROR\|<detail>` | `ERROR` | Always ERROR — the NACK prefix already means error |

The message type prefix already communicates the status. The status field is redundant and:
- Wastes bytes in every response (relevant for LoRa payload constraints)
- Adds unnecessary parsing complexity
- Introduces impossible invalid states (e.g. `BTC_ACK` with non-`SUCCESS` status) that parsers must guard against

**Proposed fix:** Remove the status field from all three response types. Simplified formats:

```
BTC_CHUNK_ACK|<session>|<chunk>|REQUEST_CHUNK|<next>
BTC_CHUNK_ACK|<session>|<chunk>|ALL_CHUNKS_RECEIVED
BTC_ACK|<session>|TXID:<txid>
BTC_NACK|<session>|<error_detail>
```

See **Story 20.4** in tasks.txt.

## Device Scanning: Second Meshtastic device silently hidden

**Issue 9: `scan_meshtastic_devices()` only showed one of two connected devices** ✅ FIXED
- `core/meshtastic_utils.py`'s `scan_meshtastic_devices()` delegated entirely to
  `meshtastic.util.findPorts()`, which filters serial ports to a hardcoded VID
  whitelist (Adafruit `0x239a`, Espressif `0x303a`) and only falls back to
  "everything not blacklisted" when **zero** whitelisted-VID ports are found.
- With two real devices connected — one Espressif-VID (whitelisted) and one
  Seeed-VID `0x2886` (neither whitelisted nor blacklisted) — the whitelist
  branch found a hit and short-circuited, so the Seeed device never appeared
  in the GUI's device dropdown at all.
- Not related to the Story 22.2 client/sender.py refactor; a pre-existing gap
  in the upstream `meshtastic` library's heuristic.
- Fix: `scan_meshtastic_devices()` now enumerates ports directly via
  `serial.tools.list_ports.comports()`, filtering only by `meshtastic.util`'s
  (narrow) blacklist, reusing `eliminate_duplicate_port()` for the legitimate
  same-device-listed-twice case. All non-blacklisted devices now surface.
- Tests updated in `tests/test_meshtastic_utils.py` and `tests/test_btcmesh_gui.py`
  to mock `serial.tools.list_ports.comports` instead of `meshtastic.util.findPorts`.

## Device Connection: GUI got permanently stuck / first device in list unselectable

Found while manually testing the Issue 9 fix above with two real devices
connected — both bugs only surface with 2+ real devices, which the
`findPorts()` whitelist bug had made impossible to hit before now.

**Issue 10: Transient connect error left the GUI stuck forever** ✅ FIXED
- `btcmesh_gui.py`'s `_init_meshtastic()` treats `"resource temporarily
  unavailable"` / `"busy"` errors from `MeshtasticSerialTransport.connect()`
  as transient, showing "Device is initializing, please wait..." — but there
  was no retry and no timeout anywhere. The connection attempt simply ended
  there, leaving the GUI stuck on that message permanently with no recovery
  short of restarting the app.
- Reproduced by selecting one device, then quickly selecting a second device
  before the first had fully disconnected — the second device's
  `SerialInterface` open transiently failed and the GUI hung.
- Separately, `_disconnect_device()`'s background close of the previous
  transport silently swallowed any exception (`except Exception: pass`),
  so a failed disconnect gave no visible indication that a port might still
  be locked.
- Fix: `_init_meshtastic()` now retries up to `CONNECT_MAX_ATTEMPTS` (4) times
  with a `CONNECT_RETRY_DELAY_SECONDS` (1.5s) delay between attempts on a
  transient error, reporting `connection_error` if it still hasn't succeeded
  after all attempts instead of hanging indefinitely. `_disconnect_device()`
  now logs a warning message (via the existing `'log'` result type) instead
  of silently discarding disconnect failures.
- Tests added in `tests/test_btcmesh_gui.py`
  (`TestDeviceConnectionRetryAndSelectionFix`):
  `test_init_meshtastic_retries_transient_error_then_succeeds`,
  `test_init_meshtastic_gives_up_after_max_attempts`.

**Issue 11: First device in a multi-device list couldn't be selected** ✅ FIXED
- When multiple devices are found, `_handle_result()`'s `'devices_found'`
  handling set `device_spinner.text = devices[0]` as a display-only
  placeholder (explicitly not auto-connecting, to let the user choose).
- Kivy's `Spinner.text` (a `StringProperty`) only dispatches its `on_text`
  event when the value actually *changes*. Since the placeholder was set to
  the exact same string as the first dropdown option, selecting that first
  device again from the dropdown didn't change `.text` at all — so
  `on_device_selected` never fired, and nothing happened. Selecting a
  *different* device worked fine (the text genuinely changed), and then
  going back to the first device also worked (now a real change from the
  second device's text).
- Fix: use a new placeholder constant `SELECT_DEVICE_TEXT` ("Select a device
  to connect...") that never collides with any real device path, so any
  device selection — including the first one — always registers as a text
  change.
- Tests added: `test_devices_found_multiple_sets_placeholder_not_first_device`,
  `test_on_device_selected_ignores_placeholder_text`.

## Transport: Failed handshake leaked the serial port lock

**Issue 12: A connect() failure during the device handshake leaked the open
serial port and reader thread** ✅ FIXED
- Found while investigating a real `"Timed out waiting for connection
  completion"` error from `meshtastic.serial_interface.SerialInterface()`
  (an upstream 30s wait for the device's config handshake to finish).
- `SerialInterface(devPath=...)` (default `connectNow=True`) performs the
  entire handshake *inside its own constructor* — opens the serial port,
  starts a background reader thread, sends `want_config_id`, then blocks on
  `_waitConnected()`. If that wait times out, the exception is raised from
  inside `__init__`, so `iface = SerialInterface(...)` in
  `transport/meshtastic_serial.py`'s `connect()` never completes its
  assignment. That left no reference to the already-opened port/reader
  thread to call `.close()` on — leaking an exclusive OS-level lock on the
  serial port for the rest of the process's lifetime (confirmed via `lsof`:
  the port stayed locked by the running process even after the connection
  attempt had already failed and raised).
- Verified live against real hardware: reproduced the exact timeout with the
  plain `meshtastic` library directly (bypassing our code entirely), proving
  the timeout itself isn't caused by btcmesh — but the leak was.
- Fix: construct with `connectNow=False` (opens the port but skips the
  handshake), then call `iface.connect()` / `iface.waitForConfig()`
  ourselves in a try/except that calls `iface.close()` on failure — so we
  always keep a reachable reference to clean up, even when the handshake
  fails partway through.
- Test added in `tests/test_meshtastic_serial_transport.py`:
  `test_connect_closes_iface_when_handshake_times_out`.
- Note: the underlying 30s handshake timeout itself is a real, separate
  device/firmware-level behavior (in this case traced to both test devices
  being stuck mid-boot from rapid repeated connect/disconnect cycles during
  testing — resolved by a physical power cycle) and isn't something this fix
  changes; this fix only prevents the *leak* when that timeout occurs.

## Known Nodes: Crash sorting nodes with lastHeard=None

**Issue 13: `get_known_nodes()` crashed when a node's lastHeard was explicitly
None** ✅ FIXED
- Found by manually testing the client GUI's "Scan for nodes" button (the
  first time this feature was exercised end-to-end against a real, long-lived
  node database of 71 nodes — earlier testing past days only exercised device
  scanning/connecting via one-off scripts, never this code path through the
  actual running GUI).
- `core/meshtastic_utils.py`'s `get_known_nodes()` extracted each node's
  timestamp via `node_data.get('lastHeard', 0)`. `dict.get(key, default)`
  only applies the default when the key is *missing* — not when it's present
  but explicitly `None`, which is how the `meshtastic` library represents a
  node it knows about (via mesh gossip/NeighborInfo) but has never actually
  received a packet from directly. The resulting `None` then crashed
  `nodes.sort(key=lambda n: n['lastHeard'], reverse=True)` with
  `TypeError: '<' not supported between instances of 'NoneType' and 'int'`
  as soon as at least one such node existed alongside nodes with real
  timestamps.
- Real, pre-existing bug unrelated to the Story 22.3/22.4 rename work or
  Issues 9-12 — confirmed against real hardware: of the device's 71 known
  nodes, 3-4 had `lastHeard: None`.
- Fix: `(node_data.get('lastHeard') or 0)` instead of
  `node_data.get('lastHeard', 0)`, normalizing both "key missing" and
  "key present but None" to `0` uniformly.
- Test added in `tests/test_meshtastic_utils.py`:
  `test_sorts_without_crashing_when_lastheard_is_none`.

## Known Nodes: lastHeard doesn't reflect recent direct-message traffic

**Issue 14: Known-nodes sort order may not reflect recent BTC_TX/ACK protocol
exchanges** 🔍 SUSPECTED / OPEN — needs further investigation another day

- Observed while testing two real devices that had confirmed, successful
  bidirectional BTC_TX/ACK protocol message exchanges earlier the same day
  (verified via actual successful client/server test runs, in both role
  directions). Despite that, each device's `lastHeard` entry for the other
  was still 147-255 days stale — not refreshed by that day's traffic at all.
- Ruled out so far:
  - Not the Issue 13 crash/None-handling bug (separate, already fixed).
  - Not a hardware/antenna/range issue (physically confirmed fine).
  - Not a LoRa config mismatch (`region`, `modem_preset`, primary channel
    name and PSK all verified identical on both devices).
  - Sending a fresh direct text message live during investigation and
    reconnecting ~70s later still showed no update to the peer's `lastHeard`.
- Current best hypothesis: Meshtastic's `lastHeard` NodeDB field tracks mesh
  *presence* — updated by periodic broadcast beacons (NodeInfo, Position,
  Telemetry announcements) — rather than direct, addressed application
  messages like our BTC_TX/ACK protocol traffic. The `meshtastic` Python
  library's `_onTextReceive()` → `_receiveInfoUpdate()` does wire up a
  `lastHeard` update for received text messages, but that may only affect
  the actively-connected client's own in-memory session view, not what the
  device firmware persists into its onboard NodeDB (the authoritative source
  re-sent to any client on reconnect, which is what `get_known_nodes()`
  reads). Not yet confirmed against firmware source/documentation.
- Practical effect: `get_known_nodes()`'s sort-by-`lastHeard`-descending is
  working exactly as designed, but the underlying data may not represent
  what a user intuitively expects ("recency of any successful contact,
  including our own protocol's direct messages") — it may only represent
  recency of unrelated mesh presence beacons.
- Next steps to investigate: confirm against Meshtastic firmware
  source/docs whether direct/unicast application packets update the onboard
  NodeDB's `lastHeard` at all; if not, consider whether btcmesh should track
  "last successful protocol exchange" separately from the device's own
  NodeDB-reported `lastHeard` for display purposes.

## Reassembler: no enforcement of strict in-order chunk arrival

**Issue 15: `TransactionReassembler.add_chunk()` allows a session to be
created by (or a chunk added out of order into) any chunk_num, not just the
next expected one** 🔍 OPEN — follow-up, not part of Story 23.1

- Found while reviewing `server/receiver.py`'s (Story 23.1) test coverage
  for malformed/mismatched chunks and discussing edge cases in
  `core/reassembler.py`'s `add_chunk()`.
- Traced through the actual logic: if a brand new session's *first* seen
  chunk is, say, `2/3` (not `1/3`), `add_chunk()` happily creates a session
  with `total_chunks=3` (taken from that message) and stores chunk 2 under
  key `2` — no error, no NACK. It just waits for chunks 1 and 3 to arrive
  before reassembling (order-independent at completion time, since it
  iterates `1..total_chunks` from a dict keyed by chunk_num).
- Separately, `TransactionReceiver._on_message()`'s ACK logic naively sends
  `REQUEST_CHUNK|{chunk_num + 1}` — for a chunk `2/3` this asks for chunk 3
  next, even though chunk 1 is the one actually still missing. Inherited
  unchanged from the original `btcmesh_server.py` logic, not introduced by
  Story 23.1.
- In practice this shouldn't occur with our own `TransactionSender` client,
  which only ever sends chunks strictly in order (1, 2, 3, ...) in a
  stop-and-wait fashion, waiting for each ACK before sending the next. This
  is a latent robustness gap for any other/future client implementation
  that might send out of order, or a duplicate/retransmission race, not an
  active bug in current client/server behavior.
- Discussed and decided as a deliberate scope decision: **not** folding this
  into Story 23.1 (which only extracts `server/receiver.py`'s orchestration
  around the *existing, unchanged* `TransactionReassembler`) — this would
  touch shared production code (`core/reassembler.py`, used by the
  *current* `btcmesh_server.py` too) and its existing test suite, better
  done as its own focused change.
- Agreed design direction for whenever this is picked up: reject only the
  out-of-order chunk (NACK it) while leaving the in-progress session alive,
  so the actually-expected next chunk can still arrive and complete
  reassembly normally — rather than discarding the whole session (as a
  `total_chunks` mismatch currently does), which would kill otherwise-
  recoverable progress over one anomalous/duplicate message.

## Transport: Unreliable/inconsistent chunk delivery between two specific devices

**Issue 16: ESP32→Seeed chunk delivery intermittently fails completely, with
no consistent root cause identified** 🔍 OPEN — documented as environmental
limitation, not a code bug

- Found while pausing Story 23.2 to investigate a user report: sending a
  full transaction from the ESP32 device (as client) to the Seeed device
  (as server) consistently failed - the server's log showed **zero** chunks
  ever received, across repeated attempts, using both `btcmesh_client_cli.py`
  and `btcmesh_client_gui.py` as the sender, and both the current (old)
  `btcmesh_server_gui.py` and a direct `TransactionReceiver` test script as
  the receiver. The reverse direction (Seeed client → ESP32 server) worked
  reliably (occasional single retries, normal for LoRa).
- Investigated and ruled out, in order:
  1. **My Story 23.1 destination-filter fix** (`transport/meshtastic_serial.py`)
     — ruled out because the *old* `btcmesh_server.py` (which doesn't use
     that transport at all) also received nothing in the failing direction.
  2. **EU868 duty-cycle exhaustion on the ESP32** (both devices are
     configured for the EU_868 region, which enforces a strict transmit
     duty cycle in firmware) — ruled out because ESP32 successfully
     transmitted ACK/NACK replies back to Seeed in the working direction,
     proving its radio could still transmit.
  3. **Packet-size-dependent reliability** (full ~190-byte chunk messages
     failing while short ~35-byte ACK messages succeed on the same
     ESP32→Seeed link) — looked promising initially (matched the pattern of
     that specific test), but a direct, protocol-bypassing raw-message test
     (a plain short text message and a full-chunk-sized text message, sent
     directly via `transport.send()`, no BTCMesh chunking/ARQ involved)
     showed **even the short message failing to arrive** in that test run -
     contradicting the clean size-based explanation.
- Given the inconsistent, contradictory results across repeated live tests
  (the same class of message succeeding in one run and failing outright in
  another), this looks like general RF/hardware unreliability specific to
  this pair of devices, rather than an isolatable software bug:
  - Possible marginal RF link / antenna quality on one or both devices
  - Possible mutual interference from the two radios being physically very
    close together (receiver desensitization from a nearby active
    transmitter is a known real-world LoRa phenomenon)
  - Possible timing/settling sensitivity shortly after `connect()`, similar
    to the flakiness already seen and documented in Issue 12
- Not pursued further as a code fix since the signal itself isn't
  reproducible/consistent enough to isolate. If this resurfaces, worth
  re-testing with a different pair of physical devices to determine whether
  it's specific to this exact hardware pair, or trying a longer physical
  separation between the two devices to rule out mutual interference.
- **Retested 2026-07-19** while closing out Story 23.2's deferred real-hardware
  verification (both devices freshly power-cycled). Real connections (Meshtastic
  serial handshake + Bitcoin RPC over Tor) succeeded cleanly on both devices this
  time - the earlier "wedged, needs a power cycle" state was transient, not
  reproduced. Sent a real transaction (15 chunks) in both directions:
  - ESP32→Seeed (client `!3364d5a8` → server `!aee5ab3c`): failed exactly as
    before - **zero** chunks ever reached the server across all 4 attempts of
    chunk 1.
  - Seeed→ESP32 (client `!aee5ab3c` → server `!3364d5a8`): every chunk the
    client sent was received by the server **on its first arrival** (confirmed
    from the server's own logs, including chunks the client itself had to
    retry) - it was the **ACK replies travelling back to the client** that were
    being lost, not the chunks. This caused repeated client-side retries of
    chunks the server already had (correctly deduplicated and re-ACKed each
    time), and the transaction ultimately failed when chunk 3's retries were
    exhausted (4 attempts) purely from ACK loss, even though the server had
    held that chunk correctly since its first attempt.
  - This narrows the hypothesis: in the Seeed→ESP32 direction specifically,
    the forward (chunk) path is solid but the return (ACK) path is lossy
    enough to exhaust the current retry budget. Combined with the
    ESP32→Seeed direction still failing completely, this continues to look
    like an asymmetric RF/hardware issue tied to this specific device pair
    rather than anything in `server/receiver.py` or `client/sender.py` -
    confirmed by watching both `TransactionReceiver`'s duplicate-chunk
    handling and the client's stop-and-wait retry logic behave exactly as
    designed throughout.
- **Retested 2026-08-22 with a different device pair** (Seeed `!aee5ab3c` +
  Heltec `!7c5b4418`, no ESP32 involved), ahead of a planned demo, to check
  whether this is specific to the ESP32 or a broader hardware/RF issue. Sent
  the same real 15-chunk transaction via `btcmesh_client_cli.py`/
  `btcmesh_server_cli.py` in both directions:
  - Seeed→Heltec: all 15 chunks delivered and ACKed on first attempt, zero
    retries.
  - Heltec→Seeed: all 15 chunks delivered and ACKed on first attempt, zero
    retries.
  - Both directions clean, with no sign of the chunk-loss or ACK-loss
    asymmetry seen with the ESP32. This points toward the ESP32 (or its
    specific proximity/pairing with the Seeed) as the likely locus of Issue
    16, rather than a general limitation of this codebase's LoRa link
    handling. Not conclusive on its own (Issue 12's flakiness shows single
    clean test runs aren't always reproducible), but a meaningfully positive
    signal for using the Seeed+Heltec pair at the demo instead of the ESP32.
  - Separately, this test surfaced an unrelated finding: the Bitcoin RPC
    broadcast step failed both times (`Connection refused` to the
    configured `.onion` node - Tor not reachable from this test), so full
    end-to-end broadcast success wasn't verified. Tracked as a to-do in
    `todo.txt` ahead of the demo.

## Protocol: Client retries after server has already completed the session

**Issue 17: If the final chunk's ACK or the broadcast ACK/NACK is lost in
transit, the client retries the last chunk - but the server has already
deleted the (now-completed) session, so the retry starts a confusing new
one** ✅ RESOLVED

- Found while testing: "if all chunks do get properly
  received, reassembled and broadcasted on server side, [and] the ACK or
  NACK after receiving all chunks is not received by the client, the client
  will retry sending the last chunk. While the server side already finished
  the session. So triggering a new session start at server and client never
  knowing it did actually get received, reassembled and/or broadcast
  already."
- Traced through `core/reassembler.py`'s `add_chunk()`: on successful
  reassembly (last chunk received), the session is deleted immediately
  (`del sender_sessions[tx_session_id]`) before the RPC broadcast even
  happens. If the chunk-level `BTC_CHUNK_ACK|...|ALL_CHUNKS_RECEIVED` or the
  final `BTC_ACK`/`BTC_NACK` reply is lost on the way back to the client,
  the client's own retry (same `session_id`, same last `chunk_num`) arrives
  at a server that has no memory of that session anymore - `add_chunk()`
  treats it as chunk 1 of a *brand new* session (since the session key was
  deleted), waits for the other chunks that will never come (the client
  isn't resending those, since it already got their ACKs), and eventually
  times out via `cleanup_stale_sessions()`, sending the client a confusing
  NACK for a transaction that was, in fact, already successfully processed
  (possibly already broadcast to the network) minutes earlier.
- This is a real, structural gap in the protocol's idempotency: the server
  has no way to recognize "I've already completed session X for sender Y"
  and simply resend the cached final result, instead of either silently
  creating a bogus partial session or leaving the client in the dark about
  a transaction that actually succeeded.
- Pre-existing in the current production `btcmesh_server.py` too (not
  introduced by Story 23.1's `server/receiver.py` - the same
  session-deletion-on-completion behavior lives in `core/reassembler.py`,
  unchanged by that story).
- Not fixed yet - worth its own story. Likely direction: have the server
  retain a short-lived record of recently-completed sessions (session_id →
  final result: TXID or error) for some grace period after completion, so a
  retransmitted last chunk for an already-completed session gets the cached
  final ACK/NACK resent directly instead of spawning a new phantom session.
- **Resolved 2026-07-27**: `TransactionReceiver` now keeps a
  `(sender_id, session_id) -> (completed_at, final_message)` cache,
  populated the instant a session's final ACK/NACK is sent (success,
  broadcast failure, or "RPC not connected" - all three paths in
  `_broadcast()`). Before handing a chunk to the reassembler, `_on_message()`
  checks this cache first: if the sender+session already completed within
  `completed_session_grace_seconds` (default 300s, comfortably covering the
  client's own worst-case retry window of ~120s), the cached reply is resent
  directly and the reassembler is never touched - no phantom session, no
  confusing timeout NACK. Entries are pruned lazily (on lookup, once
  expired) and periodically (in `check_timeouts()`). Keyed on
  `(sender_id, session_id)` rather than `session_id` alone, since session
  IDs are only unique per-sender. See
  `tests/test_server_receiver.py`'s `TestTransactionReceiverCompletedSessionCache`.
- **Confirmed on real hardware** the same day: ran a real 15-chunk
  transaction end-to-end between two physical devices (RPC unreachable in
  this environment, so the session completed via the "Bitcoin RPC not
  connected" NACK path); then manually resent the exact same last-chunk
  wire message to simulate "client never got the NACK." The server's log
  shows no second "New reassembly session started" line (proof `add_chunk()`
  was never reached) and immediately resent the identical
  `BTC_NACK|<session>|Bitcoin RPC not connected` - confirming the cache-hit
  path fires correctly outside of mocks too.

## Protocol: Generic reassembly errors give the client only a silent timeout, no NACK

**Issue 18: When `add_chunk()` raises a generic `ReassemblyError` or a
completely unexpected `Exception`, the server logs it locally but sends
nothing back to the client at all** ✅ RESOLVED

- Found while adding test coverage for `server/receiver.py`'s `_on_message()`
  during Story 23.3 (these two branches had zero test coverage anywhere
  before that). Pre-existing behavior in both the old `btcmesh_server.py`
  and the current `server/receiver.py` - not introduced by this story.
- The two *specific* validation errors (`InvalidChunkFormatError`,
  `MismatchedTotalChunksError`) both call `_send_nack(...)` immediately,
  giving the client a fast, informative failure. The generic
  `except ReassemblyError` and `except Exception` branches right below them
  only fire the `on_error` callback (server-side logging/UI notification)
  and return - no `BTC_NACK` is ever transmitted.
- From the client's side (`client/sender.py`), this is indistinguishable
  from the chunk or its reply simply getting lost over LoRa: it waits
  `DEFAULT_ACK_TIMEOUT` (30s), gets nothing, retries the same chunk, up to
  `DEFAULT_MAX_RETRIES` (3) times - roughly 2 minutes total - before finally
  failing with a generic `"Chunk N: timeout after 3 retries"`. The actual
  server-side error message is never seen on the client side at all,
  only by whoever has access to the server's own logs/Activity Log - in this
  project's mesh-relay design, frequently a different person on a different
  device entirely.
- Likely direction: have this fallback branch also send a generic NACK
  (e.g. `BTC_NACK|<session>|Internal server error`) instead of staying
  silent, so the client fails fast with at least some signal instead of
  waiting out the full retry timeout for a content-free failure.
- **Update 2026-07-26: a concrete real-world instance of exactly this
  pattern was found (and fixed) via live hardware testing.** With
  `rpc_client=None` (RPC failed to connect at startup - the server's own
  designed "keep running anyway" behavior), a client sent a complete,
  valid 15-chunk transaction; every chunk ACKed cleanly, reassembly
  succeeded, and then `_broadcast()` crashed with
  `AttributeError: 'NoneType' object has no attribute 'broadcast_transaction'`
  - caught by the same generic `except Exception` branch described above,
  so the client got nothing back and eventually failed with a content-free
  `"Transaction failed: No final ACK from relay"`, despite doing
  everything correctly. **Fixed**: `_broadcast()` now checks for
  `rpc_client is None` up front and sends an immediate, clear
  `BTC_NACK|<session>|Bitcoin RPC not connected` instead of attempting the
  call (see `tests/test_server_receiver.py`'s
  `test_broadcast_with_no_rpc_client_sends_nack_and_fires_callback`). This
  closes that one specific path into the generic-exception trap, but the
  broader issue - *other* generic/unexpected exceptions still get no NACK -
  remains open.
- **Resolved 2026-07-27**: both remaining branches in `_on_message()` now
  send a NACK before returning. The generic `except ReassemblyError`
  branch sends the exception's own message (these are still
  business-logic-controlled, wire-safe strings, same as
  `InvalidChunkFormatError`/`MismatchedTotalChunksError` above). The
  catch-all `except Exception` branch sends a fixed, generic
  `BTC_NACK|<session>|Internal server error` instead - deliberately *not*
  the raw exception text, since that's unconstrained and could leak
  internal details (file paths, attribute names, etc.) onto the wire; the
  real message still reaches `on_error` for whoever has access to this
  side's logs. Both NACK sends are wrapped in their own `try/except` so a
  second failure (e.g. the transport itself is also broken) can't escape
  the handler and crash whatever's dispatching messages to it. See
  `tests/test_server_receiver.py`'s
  `test_generic_reassembly_error_sends_nack_and_fires_on_error`,
  `test_unexpected_exception_sends_generic_nack_and_fires_on_error`, and
  `test_secondary_nack_failure_does_not_escape_the_generic_handler`.

**Issue 19: `uhubctl`-based power cycling (Story 26.1/EPIC 5) can silently
fail to cut real power - it only guarantees a USB data-link disconnect,
not a genuine VBUS power cycle** ✅ RESOLVED (via Story 26.7)

- Found while implementing and hardware-verifying Story 26.1
  (`transport/power_control.py`, `UhubctlPowerControl`), part of EPIC 5
  (Device Power-Cycle Recovery/Watchdog - see
  `project/plans/story_26_1.md`). EPIC 5 exists so a relay server can
  recover automatically from a wedged Meshtastic device (Issue 12/16)
  without a human physically unplugging/replugging it - important for
  anyone running this server unattended.
- `uhubctl` works by sending a standard USB hub-class `PORT_POWER` control
  request to the upstream hub. This is a well-documented, real limitation
  of the tool itself (see its own README/FAQ): many hub controller ICs
  advertise power-switching support in their USB descriptor without the
  PCB actually having a physical load switch wired to the downstream VBUS
  line - so the hub acknowledges the request and its own status register
  updates correctly, the OS loses the data connection (which looks exactly
  like a real power-off from software: `scan_meshtastic_devices()` stops
  finding the port, a `connect()` attempt mid-outage times out), but the
  device **never actually loses power**.
- **Verified with real hardware**: testing against two different hubs in
  an actual deployment (one bus-powered off a second hub, one with its own
  independent power input - i.e. both a "ganged" and, separately, a
  higher-power hub were tried) confirmed this failure mode directly by
  physically watching the connected devices' status LEDs during a held
  `off` state. In both cases the LEDs never went dark, despite `uhubctl`
  reporting success and the hub's own status register reading `off`.
  Restoring power brought both devices back immediately, confirmed
  functional via real `connect()` calls.
- **Why this matters for any deployment**: a data-link-only
  disconnect/reconnect does not reset a hung device's firmware, so
  `UhubctlPowerControl` cannot be trusted to actually recover a wedged
  device unless the specific hub in use is independently confirmed to cut
  real VBUS power - `uhubctl`'s own FAQ recommends testing this with a
  phone or USB light before relying on it for anything. Anyone deploying
  this project's watchdog feature should not assume "the hub is
  `uhubctl`-compatible" is sufficient; it must be verified.
- Buying a hub with genuinely working, verified real power switching is
  one valid path (some specific models are documented as verified-real
  ppps hubs by the `uhubctl`/Raspberry-Pi community), but suitable current
  options can be expensive or hard to reliably source, and hardware
  revisions of the "same" model can silently differ even when a listed
  model is found.
- **Resolution direction**: Story 26.7's DIY relay-based power control
  (an ESP32 driving a small relay module, spliced into a device's own USB
  VBUS wire directly) is hardware-independent - it doesn't rely on
  whatever hub happens to be upstream, or on its power-switching claims
  being accurate. This is being promoted from a conditional fallback to
  the epic's primary, recommended approach, since it's the only one that
  provides a real guarantee regardless of what hub is upstream. See
  `project/plans/story_26_7.md`.
- `transport/power_control.py`'s `UhubctlPowerControl`/`BasePowerControl`
  remain valid, tested, and available for anyone whose hub genuinely
  supports real VBUS switching (verified per the FAQ's phone-charging
  test) - they are a legitimate, simpler option when that's confirmed true.
  Story 26.7 exists for everyone else, or for anyone who'd rather not
  depend on hub compatibility at all.
- **Resolved via real-hardware verification of Story 26.7's DIY relay**:
  an ESP8266 (NodeMCU) driving a 5V relay module, spliced into a real
  Meshtastic device's own USB VBUS wire, was confirmed to **genuinely cut
  power** - this time verified with the same rigor that caught the
  original problem: physically watching the *device's own* LED (not just
  the relay's indicator LED) go dark during a `power_cycle()` call, then
  confirming a clean, functional reconnect afterward (~4.5s, correct node
  ID) via `SerialRelayPowerControl`/`MeshtasticSerialTransport`. This
  closes the gap `uhubctl` couldn't reliably close on this hardware. See
  `project/plans/story_26_7.md` for the implementation and full
  verification notes.
- **Lesson learned during this verification, worth keeping in mind for
  anyone building the same thing**: a relay's trigger polarity can't be
  fully trusted from its jumper label or even a manual "touch the IN pin
  to 3.3V/GND" test alone - one relay module tested during this work
  responded correctly to a manual touch test in one jumper position, but
  only actually toggled correctly end-to-end (i.e. in response to a real
  `power_cycle()` call from the host) in the *other* jumper position. The
  only fully reliable check is an actual end-to-end test: send a real
  cycle command and watch the relay respond to it, not just probe the
  input pin manually.

**Issue 20: `DeviceWatchdog` recovery cycles can repeatedly re-trigger
before a slow-to-enumerate device finishes rebooting, defeating recovery
even though the relay itself works correctly** ✅ FIXED

- Found while hardware-testing Story 26.5's server wiring
  (`btcmesh_server_cli.py` + `core/device_watchdog.py`) for real, end to
  end: running the actual server against a Meshtastic device wired
  through a CP2102 USB-to-UART bridge dongle, with the Story 26.7 relay
  spliced into that dongle's VBUS line.
- **Reproduction**: with the server running and connected, the device's
  serial port (`/dev/cu.usbserial-0001` / its `/dev/cu.SLAB_USBtoUART`
  alias) disappeared from the OS's port list on its own (cause unclear -
  possibly related to an earlier manual USB replug during the same
  session). `DeviceWatchdog`'s next heartbeat correctly called
  `check_alive()`, got `False`, and correctly triggered a real recovery
  cycle - confirmed physically (the device's own LED was watched cutting
  out and coming back on each cycle, matching the log). But
  `_wait_for_device()` (60s default `max_reenumerate_wait_seconds`)
  consistently timed out without finding the device again - reproduced
  identically across **6 consecutive real recovery attempts** (each
  cycle taking ~110s: 60s wait + power-cycle overhead + immediate
  re-trigger), all logging `"Automatic device recovery failed: Device
  did not reappear within the wait window"`.
- **Root cause**: because a failed recovery leaves the transport
  disconnected, `DeviceWatchdog`'s very next heartbeat tick (60s later)
  immediately calls `check_alive()` again, which returns `False` for a
  disconnected transport without attempting any device call -
  re-triggering another full recovery cycle (another power cut) right as
  the device might be mid-boot from the previous one. This device just
  takes longer than the default 60s `max_reenumerate_wait_seconds` to
  fully reboot and re-enumerate as a serial port after a real VBUS power
  cycle (plausibly a slower/different re-enumeration path for a CP2102
  bridge dongle than whatever board Story 26.7's original verification
  used, which measured only a ~4.5s reconnect) - but the self-retrigger
  is what turns "somewhat slow" into "never recovers": each cycle cuts
  power again just as the device might be about to finish coming up, so
  it never gets one clean, uninterrupted window long enough to actually
  finish booting.
- **Confirmed via a second, independent, controlled reproduction** (the
  first run's initial trigger was a spontaneous disappearance with an
  unclear cause, and the observation of "goes on and off" was made while
  only partly watching - this run fixed both gaps): the
  server was restarted against a device confirmed healthy, then a
  *single* manual `SerialRelayPowerControl.power_cycle()` was fired
  directly (bypassing `DeviceWatchdog` entirely) to deterministically put
  the device in the same "gone from the OS's port list" starting state.
  That single, isolated cut+restore was clean - the device reappeared in
  a port scan within seconds, confirming the relay and the device itself
  are not inherently the problem. The very next heartbeat then correctly
  found the transport stale and started `DeviceWatchdog`'s own recovery -
  which then failed the same way, 4 more times in a row (5 cycles total
  across both runs). Critically, a port scan taken *while the 4th cycle
  was still in progress* caught the device already back and present -
  moments before the next automatic retry cut its power again. The
  device was confirmed rebooting during the tracked
  cycle, then again just seconds later as an immediate follow-on reboot -
  consistent with the device being caught mid-boot by the next cut, not
  with the relay's own 15s off-timer. Stopping the server (halting the
  retries) let the same device settle back to fully functional within
  seconds, exactly as in the first run.
- **Why this matters**: as implemented, `DeviceWatchdog` has no cooldown
  between *failed recovery cycles* (only backoff *within* a single
  cycle's re-scan polling, per Story 26.4) and no configurable
  `max_reenumerate_wait_seconds` (a deliberate Story 26.5 scope
  decision, to avoid speculative config surface - see
  `project/plans/story_26_5.md`). For a device whose real boot+enumerate
  time exceeds the default 60s window, this combination means automatic
  recovery can loop indefinitely without ever succeeding, even though
  the underlying relay hardware and detection logic are both working
  correctly.
- **Fix**: added a `recovery_cooldown_seconds` parameter to
  `DeviceWatchdog.__init__()` (default 60.0, same order of magnitude as
  the other timing constants). `_recover()` now checks, before doing
  anything else, whether less than `recovery_cooldown_seconds` has
  elapsed since the *previous* recovery cycle finished (success or
  failure, tracked via a new `_last_recovery_finished_time`) - if so, it
  returns immediately without touching the transport or the relay at
  all. This applies uniformly to both trigger paths
  (`tick()`'s heartbeat and `record_failure()`'s threshold), since both
  go through the same `_recover()` entry point. A device that fails to
  come back still gets retried automatically (nothing needed a retry
  cap or manual intervention) - it just now gets a real, uninterrupted
  settle window between attempts instead of being re-cut within about a
  second of the previous cycle giving up. No new env var/CLI config was
  added for this - `build_device_watchdog()` just relies on the new
  constructor default, consistent with Story 26.5's original decision to
  avoid speculative config surface. See `core/device_watchdog.py`
  (`_recover()`/`_recover_once()`) and `tests/test_device_watchdog.py`
  (`TestRecoveryCooldown`) for the implementation and tests.
- **Follow-up fix, found while re-verifying the cooldown fix on real
  hardware**: the cooldown correctly spaced retries out (confirmed: a
  retry that used to fire ~1s after a failure now correctly waited the
  full ~60s), but each cycle was still unconditionally power-cycling the
  device even when it had already come back on its own during the
  cooldown window - a port scan taken right before one retry confirmed
  the device was already present, yet that cycle still failed, because
  it cut power again before ever checking. Fixed by having
  `_recover_once()` try one immediate, no-power-cut reconnect pass
  first (`_try_reconnect_without_power_cycle()`); it only falls back to
  an actual `power_cycle()` if that doesn't find the device. See
  `TestRecoveryPreCheckSkipsPowerCycle`.
- **Verified on the real hardware that surfaced this issue**, with both
  fixes in place: triggered the same "gone from the OS's port list"
  starting condition via a manual `power_cycle()`, then let the running
  server's own heartbeat catch it. It recovered in ~5 seconds
  (`"Device recovered. Reconnected at /dev/cu.SLAB_USBtoUART."`) via the
  new pre-check path alone, with no additional power cycle needed - the
  device had already come back on its own by the time the heartbeat
  noticed, and this time nothing cut its power again to get in the way.

**Issue 21: Client GUI froze completely and required a force-kill after
`transport.send()` hung indefinitely on an unattended overnight-wedged
device; Abort had no effect** ✅ FIXED, all 4 fixes real-hw verified

- The client GUI and server GUI were left running unattended overnight.
  In the morning, sending a transaction logged
  "Sending chunk 1/N..." and then showed nothing further for
  approximately 5 minutes - no retry messages, meaning it never reached
  the (properly 30s-bounded) ACK-wait step at all. Clicking Abort logged
  "Abort requested..." but had no effect; the entire GUI window then
  became fully unresponsive, requiring a force-kill. Physically
  unplugging the device made no difference to the frozen application.
- **Root cause**: `TransactionSender._send_all_chunks()`
  (`client/sender.py`) calls `self.transport.send(...)` synchronously,
  with no timeout of any kind. This is the one call in the entire send
  path with no bound - the 30s ACK-wait timeout only starts *after*
  `send()` returns, and the abort flag (`_abort_event`) is only checked
  after that wait completes. If the underlying
  `MeshtasticSerialTransport.send()` → `iface.sendText(...)` call itself
  never returns, nothing in the design can ever interrupt it.
- **Why unplugging didn't help**: this points away from a simple
  OS/driver-level write() block (which physically removing the device
  would typically eventually unstick, one way or another) and toward a
  Python-level lock held inside the Meshtastic library itself - the send
  call blocked while holding it, and the whole GUI window (not just the
  Send button) freezing is consistent with the main thread eventually
  needing that same lock for something else and blocking too.
- **Why this didn't happen on the client before, and likely wouldn't
  happen the same way on the server**: the client has no
  `DeviceWatchdog` at all (Story 26.6 was explicitly decided against -
  see `project/plans/story_26_6.md`), so nothing was checking the
  device's liveness during the idle overnight stretch; a wedge could
  happen at any point and sit there completely undetected until the
  first real send tried to use the stale connection. Checking whether
  the *server* needed to recover overnight turned up a related,
  separate gap: `btcmesh_server_gui.py` (which is
  what was actually run, not the CLI) has **no `DeviceWatchdog` wiring
  at all** either - Story 26.5 only covered `btcmesh_server_cli.py`; the
  GUI wiring was explicitly scoped out as a follow-up that was never
  implemented. So the server log's silence overnight isn't evidence
  nothing went wrong - there was nothing running that would have logged
  it either way.
- **Fix direction** (see `project/plans/story_28_1.md`):
  1. Wrap `MeshtasticSerialTransport.send()`'s call to `sendText()` in a
     bounded worker-thread timeout, so a genuinely stuck call can't
     block the caller forever - fixed once at the shared transport
     layer, protecting both the client and the server.
  2. Add periodic "still alive" logging to both server entry points, so
     checking the logs later gives a positive signal the process was
     actually running, not just silence.
  3. Finish wiring `DeviceWatchdog` into `btcmesh_server_gui.py` (Story
     26.5's originally scoped-out follow-up).
  4. Revisit client-side watchdog wiring (previously decided against in
     Story 26.6) as a detection-only mode (no relay hardware assumed) -
     `build_device_watchdog()` already degrades gracefully to
     detect-only when no relay is configured, so this is a much smaller
     addition than originally scoped, and would have caught this exact
     overnight wedge before the first send attempt.
- **Fix 1 implemented and verified on real hardware**: `MeshtasticSerialTransport.send()`
  now runs `sendText()` in a worker thread with a hard
  `join(timeout=_SEND_TIMEOUT_SECONDS)` (default 10s); a timeout raises
  `TransportSendError` instead of blocking forever. See
  `transport/meshtastic_serial.py` and
  `tests/test_meshtastic_serial_transport.py::test_send_raises_timeout_error_when_sendtext_blocks`.
  Verified end-to-end with a genuinely unresponsive real device (relay
  power-cut, the same method used for Issue 20) via the new
  `scripts/hw_tests/send_timeout_test.py`:
  ```
  Cutting power for 15.0s (device will go dark)...
  power_cycle() returned - relay confirmed OK. Device should now be gone/unresponsive.
  Calling transport.send() against the now-dead connection (timeout bound: 10.0s)...
  send() raised TransportSendError after 10.0s: Send timed out after 10.0s - device may be unresponsive
  ```
  `send()` returned control after exactly the configured timeout instead
  of hanging, confirming the fix works against a real (not just mocked)
  unresponsive device.
- **A finding along the way that refines the root-cause theory above**:
  while setting up this test, connecting hit
  `SerialException: Could not exclusively lock port ... Resource
  temporarily unavailable` from a different process already holding the
  port - which surfaced that `meshtastic.serial_interface.SerialInterface`
  opens its underlying `pyserial.Serial` with `exclusive=True` **and**
  `write_timeout=0`. `write_timeout=0` means non-blocking writes at the
  pyserial level (returns immediately rather than blocking indefinitely
  on a full buffer) - which weakens the "blocked in a raw OS-level
  write() syscall" explanation for the original freeze, and further
  supports the "stuck holding a Python-level lock inside the Meshtastic
  library itself" theory instead (a lock held while blocked somewhere
  else in `sendText()`'s own logic, not in the raw write call). Fix 1
  above doesn't depend on knowing the exact mechanism - a worker thread
  + join-timeout is agnostic to *why* the wrapped call doesn't return -
  but this is worth recording for anyone investigating further.
- **Fixes 2 and 3 implemented, merged, and verified on real hardware**
  (Stories 28.2/28.3):
  2. Periodic "still alive" logging added to both `btcmesh_server_cli.py`
     and `btcmesh_server_gui.py` - an INFO
     `"Server heartbeat: alive, listening. N active session(s)."` line
     every 5 minutes, regardless of other activity. **Verified on real
     hardware, both entry points**: CLI - ran against a real connected
     device with no incoming traffic, heartbeat fired at exactly the
     5-minute mark (`02:09:58` server start → `02:14:58,702` heartbeat).
     GUI - the same message appeared in the Activity Log during the Fix
     3 real-hardware test below. See `project/plans/story_28_2.md`.
  3. `DeviceWatchdog` wired into `btcmesh_server_gui.py` (Story 26.5's
     originally scoped-out follow-up) - including a
     `record_success()`/`record_failure()` asymmetry found and fixed in
     review (added `on_transport_success` to `TransactionReceiver`,
     symmetric with `on_transport_error`, fixing the already-merged CLI
     wiring too). **Verified on real hardware**: ran `btcmesh_server_gui.py`
     for real with a relay configured, cut the connected device's power
     via the relay while idle, and watched the actual GUI process (not a
     side script) detect it, recover, and reconnect:
     `"Device appears wedged - attempting automatic recovery..."` →
     `"Device recovered. Reconnected at /dev/cu.SLAB_USBtoUART."` -
     confirmed independently at the OS level too (`lsof` showed the GUI
     process's PID now holding that device path). See
     `project/plans/story_28_3.md` for the full writeup, including a
     real-time false alarm during the test (the device's OS-level file
     descriptor went stale/orphaned within seconds of the power cut, but
     detection correctly only happens on the next heartbeat, not
     instantly - nothing was actually wrong, the timing just needed
     explaining).
- **Fix 4 implemented, not yet merged, verified on real hardware**
  (Story 28.4, branch `story-28-4`): detection-only `DeviceWatchdog`
  wired into the client GUI, reviving Story 26.6 in a smaller form - a
  dedicated background thread ticks `check_alive()` during idle time and
  reports "device appears unresponsive" in the activity log, with no
  relay/recovery hardware assumed. **Verified on real hardware**: ran
  `btcmesh_client_gui.py` for real against a device with no relay
  attached, used the documented DTR/RTS wedge recipe against it while
  idle, and confirmed the correct message sequence -
  `"Device appears wedged - attempting automatic recovery..."` →
  `"Device appears unresponsive. Please reconnect it manually..."` - the
  no-relay wording, not implying a failed automatic recovery. Also
  confirmed a clean, consistent ~60s steady-state retry cadence while
  the device remained unrecovered, and - once the device was physically
  power-cycled back to healthy - the success path too: the watchdog's
  own next retry found and reconnected it on its own
  (`"Device recovered. Reconnected at ..."`), with `self.iface` correctly
  refreshed and `_update_known_nodes()` successfully querying live data
  through it ("Found 150 known node(s)"). All three watchdog result
  paths confirmed on real hardware. See `project/plans/story_28_4.md`
  for the full writeup, including two real-world surprises along the way
  (an already-wedged device before the test even started, and an
  initially-confusing first-detection delay that turned out to be
  imprecise timestamp tracking, not a bug).
- **Fix 4 superseded 2026-08-23** (not reverted for being wrong - it
  worked, and was merged and real-hardware verified as described above -
  but the architecture it was built for changed underneath it): a
  broader revision decided the client GUI should hold no ambient
  Meshtastic connection at all while idle, connecting only at the
  moment Send is actually pressed (see
  `project/plans/story_27_1.md`'s "Architecture Revision" section).
  Fix 4's entire premise was periodically pinging an *already-open*
  idle connection to catch a wedge before Send - with no idle
  connection left to ping, that premise no longer applies, and the only
  way to preserve some form of idle liveness-checking would be
  periodic *reconnect* attempts purely to test liveness - which is the
  exact rapid-reconnect-cycling pattern this project has independently
  caught **causing** real wedges (Issue 12, and a Seeed wedge
  personally reproduced during 2026-08-22's Story 27.2 hardware
  testing). So idle liveness-checking would work against itself under
  the new model, not just become redundant.
  Issue 21's original failure mode (freeze discovered only at Send
  time, with no way to abort) stays fixed regardless: Fix 1 (the bounded
  `transport.send()` timeout) is untouched and still the actual
  guarantee against a hang, and a wedge is now *always* discovered at
  Send time by construction (there's no other time a connection exists
  to wedge), with `_connect_with_retry()`'s existing retry loop plus
  Fix 1's send timeout giving a clear, immediate, actionable error
  instead of a background maybe-warning. Fix 4's client-side code was
  removed in the same revision (`btcmesh_client_gui.py`'s
  `_start_watchdog_thread`/`build_device_watchdog` wiring).
- **Status**: Fixes 1-3 implemented, merged, and verified on real
  hardware (Fix 3's server-GUI watchdog is unaffected by the above -
  the server still holds a genuinely long-lived connection for its
  whole operating lifetime, so its watchdog's premise still applies).
  Fix 4 implemented, merged (PR #38), verified on real hardware, then
  superseded per above. See `project/plans/story_28_1.md` for the full
  epic tracking doc.

**Issue 22: Server device wedges far more often overnight than during
active use - root-caused to macOS system sleep, not a code bug** ✅
EXPLAINED, no code fix needed

- The server GUI and client GUI (`btcmesh_server_gui.py` and
  `btcmesh_client_gui.py`, the same two processes used for the Story
  28.3/28.4 real-hardware tests above) were left running unattended
  overnight. The server device wedged repeatedly, often after only 2-3
  "alive" heartbeats, but always recovered on its own (even across port
  changes). It also stayed alive for more heartbeats while the laptop was
  actively in use, and wedged sooner while the laptop sat idle -
  suggesting a link to the laptop's own sleep behavior rather than a flaw
  in the recovery logic itself.
- **Investigated with `pmset -g log`** (macOS's own sleep/wake history),
  correlated against the two process start times (server GUI 02:24,
  client GUI 02:38): the Mac entered genuine 'Idle Sleep' at 03:19 -
  about 45-55 minutes after both processes started, presumably once
  active use stopped - then cycled through Sleep -> DarkWake -> Sleep
  roughly every 10-20 minutes continuously until the laptop was used
  again at 11:59 (`"Wake from Deep Idle ... UserActivity"` - the exact
  moment activity resumed). That's dozens of real system-sleep cycles
  overnight.
- **Why this explains the whole pattern**: macOS suspends/resets USB bus
  power around system sleep/wake, which would genuinely disrupt a
  USB-attached Meshtastic device on every cycle - not a wedge caused by
  the application, the transport layer, or the watchdog. This lines up
  exactly with what was observed: frequent wedges only once real sleep
  cycles start (i.e. once the laptop goes idle), no such disruption while
  the laptop is actively in use (no full sleep happening), and successful
  recovery every time - including across port changes - is precisely
  what Story 28.3's `DeviceWatchdog` wiring is designed to do when the
  device re-enumerates under a new OS path.
- **Conclusion**: this is not a defect in Issue 21's fixes - if anything
  it's a strong, unplanned overnight stress test of Story 28.3's recovery
  path (dozens of real disrupt/recover cycles, all handled correctly with
  no manual intervention). The high *frequency* is an artifact of running
  an unattended relay server on a machine with default laptop power
  settings, not a bug to fix in this codebase.
- **Recommendation (operational, not code)**: a machine intended to host
  the relay server unattended (overnight or otherwise) should have system
  sleep disabled, or be run under `caffeinate -s` (prevents system sleep
  while the process runs; display can still sleep independently). This
  avoids the disrupt/recover churn entirely rather than just tolerating
  it well. No project code change is implied by this - it's a deployment
  note, not a story.
- **Status**: Root-caused and explained; no story opened, since the
  correct fix is a machine/deployment setting, not application code. The
  watchdog behavior that made this survivable in the first place is
  already covered by Story 28.3/28.4's real-hardware verification above.

## Server: Seeed (ESP32-S3 native USB) exhibits recurring real USB pipe-stalls, unrelated to Issue 22's sleep/wake cause

**Issue 44: found while investigating Issue 40 - the Seeed's own
native-USB firmware (not a UART bridge chip) genuinely, repeatedly
stalls at the USB protocol level, independent of macOS sleep/wake or
screen lock** 🔍 OPEN (informational/environmental, no code fix)

- Found 2026-08-23 while re-investigating Issue 40 on real hardware
  (server on Seeed, client on Heltec): user reported the server's
  watchdog cycling through wedged/recovered/wedged repeatedly right
  after starting a send, receiving no chunks at all - a more severe
  failure than Issue 40's original scenario (chunks 1-8 succeeding,
  only chunk 9 affected). User's own hypothesis: the server itself may
  have actually wedged, its watchdog catching this too late.
- **First ruled out Issue 22's mechanism** (macOS system sleep
  disrupting USB) via the same `pmset -g log` method as that
  investigation: found a `PreventUserIdleSystemSleep "Powerd - Prevent
  sleep while display is on"` assertion held continuously throughout
  the test window with no reset, and zero Sleep/Wake/DarkWake
  transition entries at all - unlike Issue 22's clear repeated Idle
  Sleep cycles. The system never actually slept; screen lock alone
  didn't trigger it this time.
- **Root-caused instead via `/usr/bin/log show`** (macOS unified
  system log - note zsh has its own builtin `log` command that shadows
  `/usr/bin/log`; the full path is required) filtered to the test
  window and the device name:
  ```
  kernel: (IOUSBHostFamily) AppleUSBIORequest::complete: device 5
  (seeed-xiao-s3@01123000) endpoint 0x00: status 0xe0005000
  (pipe stalled): 0 bytes transferred
  kernel: (IOUSBHostFamily) AppleUSBXHCIPipe: IOUSBHostPipe::abortGated:
  device 5 (seeed-xiao-s3@01123000) endpoint 0x84: aborting 16 requests
  ```
  Real, recurring bursts of these (dozens to 75+ events per burst) at
  22:20:54, 22:22:00, and 22:22:51, tapering to smaller bursts through
  22:25 - a genuine, repeated USB protocol-level fault (control
  endpoint 0x00 stalling, forcing the OS to abort pending bulk-endpoint
  requests too), not a false-positive watchdog reading and not a
  macOS-power-management artifact.
- **Also very likely explains Issue 40's original incident, same day**:
  checked the exact same way against Issue 40's original `14:53:16`
  reassembly-timeout timestamp - found the identical pattern, including
  a hard `abortGated` abort on the Seeed's receive endpoint (0x84) at
  `14:53:12`, 4 seconds before the server's own timeout fired. Issue
  40's "asymmetric RF loss" framing has been corrected there to point
  here instead - this single hardware quirk plausibly explains both
  incidents.
- **Why this is a different mechanism from Issue 22**: the Seeed
  (`seeed-xiao-s3`, VID `0x2886`) enumerates as a native-USB CDC device
  via its ESP32-S3's own USB peripheral (TinyUSB-based firmware stack) -
  unlike the Heltec/other boards in this project's test fleet, which
  use a dedicated UART-bridge chip (CP2102/CH340) for USB-serial.
  Native-USB microcontroller stacks are known to be less mature/robust
  than dedicated bridge ICs; this looks like a firmware-level bug or
  timing issue in the Seeed's own USB stack, not anything triggered by
  the host OS.
- **This explains the observed symptom precisely**: `DeviceWatchdog`
  (`core/device_watchdog.py`) was working exactly as designed -
  correctly detecting each real stall via `check_alive()` and
  correctly recovering (`_try_reconnect_without_power_cycle()`)
  each time the device came back - but the stalls recurred faster
  than a full Meshtastic chunk-relay handshake could reliably complete
  in the windows between them, so the send never made progress despite
  the watchdog "working."
- **Not a bug in this project's code** - `DeviceWatchdog`, the transport
  layer, and the connect-retry logic all behaved correctly given a
  device that was genuinely, repeatedly faulting at the USB layer. No
  application-level fix is implied; matches Issue 22's precedent
  (environmental/hardware root cause, watchdog recovery working as
  intended, no code change).
- **Practical implication**: this is real-world evidence for *why*
  Story 26.7's relay-board automatic power-cycling exists at all - a
  device that repeatedly USB-pipe-stalls at the firmware level, rather
  than cleanly disconnecting, is exactly the kind of fault a full power
  cut (not just a reconnect attempt) is most likely to actually clear,
  which this incident didn't get to test (`RELAY_SERIAL_PORT` wasn't
  configured for this session, and `_try_reconnect_without_power_cycle()`
  kept "succeeding" often enough that the watchdog's cooldown/backoff
  never escalated to an actual power-cycle attempt).
- Not scoped or fixed here - logged as a documented, understood
  hardware quirk specific to this Seeed board's native-USB
  implementation, distinct from Issue 22.
- **Practical recovery-duration data point (2026-08-24)**: the Seeed
  wedged spontaneously overnight (client side, no `DeviceWatchdog` -
  Story 26.6 was decided against, so this needed manual recovery). A
  short (few-second) unplug/replug was **not** enough - the client GUI
  found the device again and could list known nodes, but became
  unresponsive as soon as an actual send was attempted. Unplugging
  again for **15+ seconds** cleared it fully - the client connected and
  sent normally afterward, and the transaction completed cleanly (one
  chunk-1 send needed one retry, then all 15 chunks went through
  without issue - ordinary stop-and-wait ARQ behavior, not a symptom of
  the stall). Consistent with Issue 20's finding for the server-side
  relay-triggered case (a device needs a genuinely clean, uninterrupted
  window to recover, not just a brief interruption) - worth remembering
  as practical guidance for manually recovering a wedged Seeed: don't
  assume a quick unplug was enough just because the device re-enumerates
  and looks selectable again.

## Code Review Findings (2026-08-20)

The following issues (23-35) were found via a full-codebase senior-engineer
code review rather than live testing - see `project/code_review_2026-08-20.md`
for the complete write-up with file:line citations and code snippets for each.
The two HIGH-severity items were independently verified by reading the source
directly and, for Issue 23, running a live interpreter check of the exception
hierarchy in question. All are logged here as open issues to be worked

**Issue 23: RPC retry logic never actually retries** ✅ RESOLVED
- `core/rpc_client.py:74`'s `rpc_request()` catches builtin `ConnectionError`/
  `TimeoutError` to drive its retry-with-backoff loop, but `requests.post()`
  (line 68) raises `requests.exceptions.ConnectionError`/`Timeout`, which do
  **not** inherit from those builtins - confirmed live:
  `issubclass(requests.exceptions.ConnectionError, ConnectionError) == False`.
- Every real network failure to Bitcoin Core falls into the generic
  `except Exception: raise` at lines 82-85 and is re-raised on the first
  attempt - the docstring's "automatic connection retry logic" (line 45)
  never fires for the failure mode it was written for.
- Proposed fix: catch `(requests.exceptions.ConnectionError,
  requests.exceptions.Timeout)` instead of the builtins.
- **Resolved 2026-08-20**: `rpc_request()` now catches
  `(requests.exceptions.ConnectionError, requests.exceptions.Timeout)`.
  The three existing retry tests were themselves asserting against the
  builtin exception type (exactly what let this ship unnoticed) - fixed
  to use `requests.exceptions.ConnectionError`, and `time.sleep` is now
  mocked in all four retry-path tests since the fix makes them genuinely
  sleep between attempts. Branch `code-review-cleanup`, full suite green
  (736 tests).

**Issue 24: Transaction sanity-check module is never wired into the
broadcast path** ✅ RESOLVED
- `core/transaction_parser.py`'s `decode_raw_transaction_hex()` and
  `basic_sanity_check()` are referenced only from `tests/` (confirmed via
  repo-wide grep). The path from reassembled hex to broadcast
  (`core/reassembler.py` -> `server/receiver.py:276` ->
  `rpc_client.broadcast_transaction`) never calls them, despite the module's
  own docstring describing it as built for exactly this purpose (Story 3.1).
- Effect: a malformed/garbage transaction is only rejected after the full
  multi-chunk LoRa round-trip completes, via Bitcoin Core's raw RPC error
  text, instead of a fast local check with a clean message.
- Proposed fix: call `decode_raw_transaction_hex` + `basic_sanity_check` on
  the reassembled hex in `server/receiver.py` before `broadcast_transaction`,
  NACKing locally on failure.
- **Resolved 2026-08-20**: `TransactionReceiver._broadcast()` now runs
  both checks first and NACKs locally (without touching the RPC client at
  all, and without firing `on_broadcast_started`) on decode failure
  ("Invalid transaction structure") or an empty inputs/outputs list ("No
  inputs"/"No outputs"). The existing test suite used `"deadbeef"` as a
  stand-in reassembled payload throughout `test_server_receiver.py` -
  too short to be a well-formed transaction, so it would now be rejected
  by the new check - replaced with a minimal but structurally valid
  transaction hex (1 input, 1 output) across ~40 call sites so the
  existing broadcast-success/failure paths still exercise what they
  intended to. Added 4 new tests for the rejection paths, including one
  confirming a rejected transaction still populates the completed-session
  cache (Issue 17) so a retransmit gets the same cached NACK instead of
  restarting reassembly. Branch `code-review-cleanup`, full suite green
  (736 tests).

**Issue 25: Client-side hex validation accepts strings that aren't
actually valid hex** ✅ RESOLVED
- `core/protocol.py:38-49`'s `is_valid_hex()` validates via `int(s, 16)`,
  which accepts underscore digit separators, leading/trailing whitespace,
  and a leading `0x`/`+`/`-` - none of which `bytes.fromhex()` or Bitcoin
  Core's own hex decoder accept. Since `validate_transaction_hex()` (lines
  52-63) is the sole client-side gate before chunking and sending across the
  mesh, a string like `"0xdeadbeef..."` passes validation and triggers a
  full multi-chunk LoRa transfer that only fails at the very end.
- Proposed fix: validate with a strict character-class check
  (`re.fullmatch(r'[0-9a-fA-F]+', s)`) instead of `int(s, 16)`.
- **Resolved 2026-08-20**: `is_valid_hex()` now matches against
  `^[0-9a-fA-F]+$` instead of relying on `int(s, 16)`. Added tests for
  the previously-permissive cases (`0x` prefix, leading/trailing
  whitespace, underscore separators, leading `+`/`-`). Branch
  `code-review-cleanup`, full suite green (741 tests).

**Issue 26: No upper bound on reassembly session size or count** ✅ RESOLVED
- `core/reassembler.py:129`'s `_parse_chunk()` only checks `total_chunks >
  0` - no upper bound, and no cap on concurrent open sessions per sender. A
  sender declaring `total_chunks=999999`, or opening many distinct
  `tx_session_id`s, grows `active_sessions` unbounded until the 300s
  timeout sweeps it. LoRa bandwidth limits practical severity, but it's a
  real memory-growth vector against the server process with no cap today.
- Proposed fix: add a sane max `total_chunks` (derived from a reasonable
  max tx size / `DEFAULT_CHUNK_SIZE`) and/or a max concurrent-sessions-per-
  sender cap, rejecting/NACKing chunks that exceed it.
- **Resolved 2026-08-20**: added `MAX_TOTAL_CHUNKS` and
  `MAX_CONCURRENT_SESSIONS_PER_SENDER` to `core/constants.py`.
  `_parse_chunk()` rejects a `total_chunks` beyond the first limit with
  `InvalidChunkFormatError`; `add_chunk()` rejects a new session beyond
  the second with a new `TooManySessionsError` (falls into
  `server/receiver.py`'s existing generic `ReassemblyError` NACK
  handler, no receiver.py changes needed).
- **Correction 2026-08-20**: the first pass set `MAX_TOTAL_CHUNKS = 5000`,
  justified by "largest standard Bitcoin tx size / chunk size" - a much
  weaker bound than what the transport itself allows. Recalculated from
  real LoRa airtime instead: a chunk message at this project's own
  real-hardware preset (LongFast, SF11/BW250 on EU_868 - see Issue 16)
  takes ~2s of airtime. Even a sender that ignores the region's 10%
  duty-cycle limit entirely and floods the channel back-to-back is still
  bound by that per-packet airtime, giving `DEFAULT_REASSEMBLY_TIMEOUT`
  (300s) / ~2s ~= 150 chunks as the physical ceiling for how many chunks
  could ever arrive in one session's lifetime (a real duty-cycle-
  compliant sender is far more constrained still, ~15 chunks in 300s).
  Set deliberately below even that adversarial ceiling:
  `MAX_TOTAL_CHUNKS = 50`, `MAX_CONCURRENT_SESSIONS_PER_SENDER = 5`.
  Branch `code-review-cleanup`, full suite green (748 tests).

**Issue 27: Shared abort event breaks per-session isolation in
`TransactionSender`** ✅ RESOLVED
- `client/sender.py`'s class docstring (line 199) claims "concurrent sends
  via session isolation," but `self._abort_event` (line 231) is a single
  `threading.Event` shared by the whole instance, unconditionally cleared
  at the start of every `send_transaction()` call (line 300). Two sends
  running concurrently on the same instance can silently un-abort each
  other, or wrongly abort the wrong session.
- Proposed fix: key `_abort_event` per-session (e.g. store it on
  `SendSession`, or a `Dict[str, threading.Event]`) and check the
  session's own event in `_send_all_chunks`.
- **First pass, 2026-08-20**: moved the abort flag onto `SendSession`
  (`request_abort()`/`is_aborted()`) so each session owned its own
  `threading.Event`, and gave `TransactionSender.abort()` an optional
  `session_id` parameter to target one session.
- **Reconsidered 2026-08-20**: checked whether concurrent sends on one
  `TransactionSender` instance are actually reachable by either real
  caller. They aren't: `btcmesh_client_cli.py` is a one-shot script (one
  send per process, then exit) and `btcmesh_client_gui.py`'s
  `on_send_pressed()` disables every input control (including Send)
  before a send starts and only re-enables them once it fully finishes -
  there's no UI path to trigger a second send while one is in flight,
  and it creates a fresh `TransactionSender` per send anyway. The
  docstring's "concurrent sends via session isolation" claim was
  describing a capability nothing exercises. Reverted the per-session
  abort-state change and kept the original single shared
  `threading.Event`/no-arg `abort()` design; corrected the class
  docstring instead to state the actual contract (one send in flight
  per instance - create a new `TransactionSender` per send if more are
  ever needed concurrently, same as both current callers already do).
  Replaced the per-session isolation tests with simpler ones covering
  the single-shared-event behavior (abort stops an in-progress send; a
  prior send's abort state doesn't leak into the next send on the same
  instance). Branch `code-review-cleanup`, full suite green (751 tests).

**Issue 28: RPC credentials aren't URL-escaped; diagnostic/error logging
invisible at the default log level** ✅ RESOLVED
- **Credential escaping.** `core/rpc_client.py:31` builds the RPC
  connection URI as `http://{user}:{password}@{host}:{port}` by directly
  interpolating the raw password into the URL string, with no escaping.
  Bitcoin Core places no restriction on which characters an RPC password
  can contain, so a real generated/random password can easily include
  `@`, `:`, `/`, or `#` - characters that are structurally meaningful
  inside a URL's `user:password@host` segment (`@` marks where the
  userinfo ends and the host begins; `:` separates user from password).
  If the password contains one of these unescaped, the URL parser used
  internally by `requests` can misread where those boundaries actually
  are - e.g. a password containing `@` could cause part of the password
  to be parsed as the hostname instead, silently pointing the client at
  the wrong host, instead of connecting to the real Bitcoin Core node.
  The code simply never accounted for this - it's not a hypothetical
  edge case, it's a real character set Bitcoin Core RPC passwords are
  allowed to use.
- **Logging visibility.** Separately (and unrelated to the escaping bug
  above): nearly every log call in this file is `.debug()`, but
  `server_logger` is fixed at `INFO` (`core/logger_setup.py:15`) with no
  env/config override - so this diagnostic detail (including the
  Issue 23 retry attempts, and any RPC/connection error) is invisible in
  normal operation. An operator trying to debug "why isn't my server
  broadcasting transactions" has no way to see what's actually failing
  without editing source to change the log level.
- Proposed fix: `urllib.parse.quote()` the user/password when building the
  URI; promote key RPC error logs to `.warning()`/`.error()`.
- **Resolved 2026-08-20**: `core/rpc_client.py`'s URI is now built with
  `quote(user, safe='')`/`quote(password, safe='')`, so any character in
  either field is safely percent-encoded and can never be misread as a
  URL structural character. Promoted the operationally-relevant log
  calls from `.debug()` to `.info()`/`.warning()`/`.error()` (connection
  success, retry-in-progress, retries-exhausted, RPC-level rejection,
  broadcast failures) while leaving genuinely per-call trace noise (e.g.
  "Executing RPC method... attempt N") at `.debug()`.
  **Correction to the original finding**: the "if DEBUG is ever turned
  on, `str(e)` can put the credential-bearing URL directly into the log
  file" claim was checked empirically and doesn't hold up -
  `requests`/urllib3 connection-error messages only ever include
  `host`/`port` (verified via a live `ConnectionError` against a URI
  with embedded credentials; the credentials never appeared in `str(e)`,
  even when the password itself was malformed enough to break URL
  parsing). No log-scrubbing was needed for that reason; the promoted
  log levels above are purely an operability improvement. Added a test
  confirming the URI is correctly percent-encoded and still parses to
  the intended host with special characters in the password. Branch
  `issue-28`, full suite green (752 tests).

**Issue 36: `test_btcmesh_server_gui.py`'s mocked Kivy `Button` is a
single shared instance across every button and every test in the
process** 🔍 OPEN

- Found while verifying Issue 29's fix: running
  `TestReassemblyTimeoutSettingsStory183`'s tests standalone (e.g.
  `python -m unittest tests.test_btcmesh_server_gui.TestReassemblyTimeoutSettingsStory183`)
  fails 4 tests with `AssertionError: <MagicMock name='mock.Button().disabled' ...> is not false`
  - `gui.start_btn.disabled` is a raw `MagicMock`, not the real `False`
  it should default to. The same tests pass cleanly under the project's
  actual documented test command,
  `python -m unittest discover -s tests -p 'test_*.py'` (confirmed: full
  suite green, 756/756).
- **Root cause**: the file's Kivy-mocking setup
  (`tests/test_btcmesh_server_gui.py:191-209`) gives some widget types
  their own dedicated mock class with a real `__init__` that captures
  constructor kwargs into real attributes (`MockTextInput`,
  `MockSpinner`) - but `Button`, `Popup`, and `ToggleButton` are instead
  mapped straight to a bare `unittest.mock.MagicMock()`
  (`sys.modules['kivy.uix.button'] = kivy_mock`, line 197). A bare
  `MagicMock` used as a class stand-in returns the exact same memoized
  `.return_value` object from *every* call, regardless of the
  constructor arguments passed - confirmed directly:
  ```python
  b1 = Button(text='A', disabled=False)
  b2 = Button(text='B', disabled=True)
  b1 is b2  # True
  b1.disabled = False
  b2.disabled  # False - same object, so this "leaked" too
  ```
  So every `Button(...)` call anywhere in `_build_controls_section()`
  (`start_btn`, `stop_btn`, `save_btn`, `history_btn`,
  `test_connection_btn`, etc.) - across *every* `BTCMeshServerGUI()`
  instance created in the whole test process - returns literally the
  same object. Whichever test last assigned `.disabled` on any of these
  "different" buttons leaves that value sitting there for every other
  test's buttons too, until another test overwrites it again. Running
  the full suite happens to leave it in a state that passes; running a
  narrower slice doesn't hit whatever earlier test would have reset it.
- **Why this matters**: these 4 tests aren't actually testing anything
  false-positive today (the full suite passes, which is what CI/the
  documented workflow runs), but the underlying shared-mock-instance
  bug means any test in this file that asserts on a `Button`/`Popup`/
  `ToggleButton` attribute is silently relying on execution order rather
  than genuine per-test isolation - a latent source of flaky failures
  whenever the file's test order changes (new tests added/removed/
  reordered, or someone runs a subset while debugging).
- Proposed fix: give `Button`, `Popup`, and `ToggleButton` the same
  treatment as `TextInput`/`Spinner` - a small `MockButton`/`MockPopup`/
  `MockToggleButton` class with a real `__init__(self, **kwargs)` that
  stores `disabled`, `text`, etc. as real per-instance attributes, so
  each constructed widget is a genuinely distinct object.
- **Resolved 2026-08-22.** Added `MockButton` and `MockPopup` classes
  (mirroring the existing `MockTextInput`/`MockSpinner` pattern) with
  real `__init__` methods capturing `text`, `disabled`, `bold`,
  `background_color`, `size_hint_x/y`, `width`, `height`, `font_size`,
  and (for `Popup`) `title`, `content`, `size_hint`, plus `open()`/
  `dismiss()` methods. Each now gets its own dedicated mock module
  (`button_mock`/`popup_mock`) instead of sharing the generic
  `kivy_mock` bare `MagicMock()`, so every constructed instance is a
  genuinely distinct object with its own attributes, matching what the
  real Kivy widgets do.
  `ToggleButton` was intentionally left mapped to the bare `kivy_mock`
  in this file: `btcmesh_server_gui.py` (the module this test file
  covers) never imports `ToggleButton` at all - only the client GUI
  does - so there is no real caller in this file to fix, and adding an
  unused `MockToggleButton` class here would just be dead code.

  `TestReassemblyTimeoutSettingsStory183` standalone (the case that
  originally surfaced this bug) now passes cleanly on its own, not just

## Client: Abort button doesn't interrupt a chunk stuck retrying on timeout

**Issue 38: `TransactionSender.abort()` is only checked after a chunk
gets ACKed, not while one is timing out and retrying - pressing Abort
during a stuck retry has no effect until retries are exhausted on
their own** ✅ FIXED (2026-08-23)

- Found during real-hardware verification of the client GUI's
  connect-only-at-Send revision (2026-08-23, see
  `project/plans/story_27_1.md`'s "Architecture Revision" section) -
  not caused by that revision, and not in a file it touched.
  `client/sender.py` hasn't been modified all session; this is a
  pre-existing gap independently surfaced by hands-on testing.
- Pressing Abort while a chunk is actively being retried (no ACK
  arriving) logs "Abort requested..." but has no real effect - the
  retry loop keeps going and the send eventually fails with a timeout
  error ("Chunk N: timeout after N retries") that looks unrelated to
  the abort that was actually requested, rather than stopping
  immediately with "Aborted by user".
- **Root cause**: `client/sender.py`'s `TransactionSender._send_all_chunks()`
  only checks `self._abort_event.is_set()` inside the branch where
  `_wait_for_chunk_ack()` returns `True` (an ACK actually arrived):
  ```python
  if self._wait_for_chunk_ack(send_session, chunk_num):
      # ACK received
      if self._abort_event.is_set():        # <- only checked here
          send_session.error = "Aborted by user"
          send_session.failed = True
          return
      ...
      break
  else:
      # Timeout, no ACK - retry
      max_attempts -= 1
      send_session.increment_retry(chunk_num)
      if max_attempts == 0:
          send_session.error = f"Chunk {chunk_num}: timeout after {self.max_retries} retries"
          send_session.failed = True
          return
      # <- no abort check at all in this branch - loops straight back
  ```
  The outer `while max_attempts > 0:` loop's only pre-iteration check
  is `if send_session.failed: return` - `_abort_event` itself is never
  consulted in the timeout/retry path, so aborting while stuck waiting
  for (or between retries of) an ACK that never comes is silently
  ineffective until the retry budget runs out on its own.
- **Practical effect**: in the common case a user would actually want
  to abort - a chunk that's genuinely not getting through - Abort
  doesn't work. It only works in the comparatively rare case where an
  ACK happens to arrive at the same moment.
- **Fix** (branch `issue-38`): added the exact check proposed above -
  `self._abort_event.is_set()` right after the `else` (timeout)
  branch's retry-budget check (only reached when more retries remain;
  a genuine retry-exhaustion on the same iteration still reports its
  own timeout error, same as before). Same "Aborted by user" outcome
  as the ACK-received branch, just now reachable from both paths.
- **Residual limitation, by design**: this makes Abort effective
  *between* retry attempts, not instantly mid-wait - `_wait_for_chunk_ack()`'s
  blocking `event.wait(timeout=...)` call still has to return before the
  new check runs, so Abort can still take up to one full
  `timeout_seconds` (default 30s) to take effect, not immediately. Full
  mid-wait interruption would need restructuring the wait itself (short
  polling intervals instead of one blocking call) - a larger change not
  scoped here; this fix closes the actual reported gap (Abort having
  *no effect at all* during retries, requiring the full retry budget to
  exhaust - up to `max_retries` cycles, not just one).
- **Verified**: new regression test
  (`test_abort_stops_a_chunk_stuck_retrying_on_timeout` in
  `tests/test_client_sender.py`) - a 1-chunk send with no ACK ever
  delivered, `abort()` called mid-wait, asserts the send stops with
  "Aborted by user" after roughly one timeout cycle instead of
  exhausting all retries. Full suite (814/814) passing, including the
  existing `test_max_retries_exhausted`/`test_retry_then_success` tests
  confirming normal (non-aborted) retry behavior is unaffected.
- Per this project's one-issue-one-branch convention, scoped as its own
  fix rather than folded into the Story 27.x work that was running
  when this was found.

## Client: gives up and disconnects before the server's slower reassembly-timeout NACK can arrive

**Issue 40: client's per-chunk retry budget expires (and the client
disconnects) well before the server's own reassembly-session timeout
fires, so the client app never sees the server's authoritative
`BTC_NACK|...|Reassembly timeout`** 🔍 OPEN (informational/UX gap, not
a protocol bug)

- Found during real-hardware end-to-end send verification (2026-08-23,
  server GUI + client GUI both live, Seeed + Heltec pair, see
  `project/plans/story_27_1.md`). Session `4dcfb`: server received and
  ACKed chunks 1-9 cleanly; the client's chunk-9 retransmissions
  (4 attempts total) never got their `BTC_CHUNK_ACK` reply back - the
  server had already re-ACKed the duplicate each time, but none of
  those ACK replies made it back over the mesh to the client. The
  client exhausted its own per-chunk retry budget, reported a timeout,
  and disconnected its serial transport (per the connect-only-at-Send
  `finally` block).
- Confirmed via log evidence (not just inference) that the underlying
  NACK-on-reassembly-timeout mechanism (Issue 23.3) worked exactly as
  designed on the server side:
  ```
  14:53:16 WARNING [Sender: !7c5b4418, Session: 4dcfb] Reassembly
  timeout after 120s. Received 9/15 chunks. Discarding.
  14:53:16 INFO    Identified 1 stale reassembly sessions for cleanup
  and NACK.
  [DEBUG] [Sending packet] to: 2086355992 ... payload:
  "BTC_NACK|4dcfb|Reassembly timeout"
  ```
  (120s here is this `.env`'s `REASSEMBLY_TIMEOUT_SECONDS` override,
  not the 300s default.) The client's own chunk-level timeout (several
  ACK_TIMEOUT=30s retry cycles on one chunk) is comfortably shorter
  than the server's whole-session 120s timeout, so the client always
  gives up and walks away first.
- **User confirmed via physical evidence, not just logs**: the client's
  own Meshtastic device (Heltec) audibly beeped and showed the
  incoming `BTC_NACK` on its onboard display - proving the radio
  itself received the server's NACK over LoRA on its own firmware,
  independent of whatever the host app's USB/serial connection state
  was at that moment. The client *app*, however, had already closed
  its serial connection by then and so never read or displayed it -
  the user only ever saw the app's own generic "chunk timeout" failure,
  not the server's more specific/authoritative explanation.
- **Not a protocol bug** - each side's timeout is independently correct
  given its own budget; this is a natural consequence of two
  independently-timed processes over a lossy link, not a logic error.
  A fix would mean the client either waiting significantly longer
  after its own retries are exhausted (eating into airtime/duty-cycle
  budget for a low-probability payoff - see this project's general
  lean-conservative stance on LoRA timing budgets) or staying connected
  passively post-failure just to listen for a NACK that may never come.
  Neither is obviously worth the complexity for a low-severity UX
  polish item (the end failure state is correct either way - the send
  did fail - it's only the displayed *reason* that's less specific than
  it could be).
- Not scoped or fixed here - left open as a documented, understood
  behavior rather than an active defect.
- **Correction (2026-08-23, found while re-investigating this issue)**:
  the "asymmetric RF loss on chunk 9's ACK reply" framing above is very
  likely **wrong, or at least incomplete**. Checking `/usr/bin/log show`
  (macOS unified log) for this exact session's timeframe found the
  Seeed exhibiting the same massive USB pipe-stall pattern documented
  in Issue 44 - including a hard `IOUSBHostPipe::abortGated` abort on
  its receive endpoint (0x84) at `14:53:12`, just **4 seconds** before
  the server's own `14:53:16` reassembly-timeout log line. That's not
  circumstantial - the server's transport link to its own radio was
  actively failing at the USB level at essentially the same moment the
  higher-level protocol gave up. The far more likely explanation:
  chunk 9's ACK reply (and everything after it) was lost because the
  **server's own USB connection to the Seeed was faulting**, not
  because of mesh/RF propagation loss on the reply path as originally
  assumed. See Issue 44 for the full root-cause investigation
  (confirmed independently via a fresh reproduction the same day).
  The rest of this issue's analysis (NACK-on-timeout mechanism working
  correctly, client disconnecting before it arrives) still holds either
  way - only the *reason chunk 9 got stuck in the first place* is
  corrected here, from "RF loss" to "the server-side USB link was
  faulting."
- **Targeted live-reproduction attempts for the specific scenario this
  issue names in its title (2026-08-23/24)**: to directly test whether
  the client correctly handles a reassembly-timeout NACK arriving
  *while it is still retrying*, rather than after it has already given
  up, `REASSEMBLY_TIMEOUT_SECONDS` was temporarily lowered to 20s (well
  under the client's own worst-case ~120s retry budget) and two full
  15-chunk sends were run end-to-end with both GUIs live and logs
  captured (session `7e55f`, then `46dde`). Both completed cleanly
  through all 15 chunks with no stall, retry, or reassembly timeout on
  either run - each ended in the expected
  `BTC_ACK|...|ALL_CHUNKS_RECEIVED` followed by
  `BTC_NACK|...|Bitcoin RPC not connected` (no Bitcoin Core reachable
  in this dev environment, an unrelated pre-existing limitation). The
  stuck-chunk condition this issue and Issue 44 describe is itself
  intermittent (USB pipe-stall bursts), so it didn't recur to order on
  either attempt.
- **Code-level correctness confirmed instead via a targeted unit test**:
  added `test_nack_arriving_during_a_retry_wait_is_handled_correctly`
  to `tests/test_client_sender.py` (`TestTransactionSenderErrorHandling`),
  which forces a real retry (no ACK on attempt 1) before delivering the
  NACK on attempt 2 - proving `client/sender.py`'s existing
  `_handle_nack()` (which signals every chunk's response event
  regardless of which is currently in flight) already handles a NACK
  arriving mid-retry correctly, with no code change needed. Combined
  with the two clean live sends above, this is considered sufficient
  verification for this issue; no further live-reproduction attempts
  are planned.
- `REASSEMBLY_TIMEOUT_SECONDS` should be restored from `20` back to its
  normal value once this `.env` change is no longer needed for other
  testing (left to the user - `.env` is not directly editable here).
- **Clean reproduction at normal timing, confirming the prediction
  exactly (2026-08-24)**: after `REASSEMBLY_TIMEOUT_SECONDS` was
  restored to its normal `120` and the Seeed was moved to a physically
  isolated USB path (see Issue 45), a deliberate Heltec+relay hub
  unplug/replug during session `d223d` reproduced this issue's exact
  scenario under realistic (not artificially shortened) timing: the
  client's own retry budget expired first (`"Error: Chunk 2: timeout
  after 3 retries"` - the generic message), while the server's log
  showed its `check_alive()`/reconnect cycle was still in progress at
  that moment, well before it could finish recovering and get a NACK
  out. Exactly the predicted behavior - this closes out the issue's
  investigation with a real, clean confirmation under production-like
  conditions, not just the shortened-timeout stress tests above.

## Transport: Auto-detect silently kills the connecting thread when multiple serial candidates exist

**Issue 41: `MeshtasticSerialTransport.connect(None)` (Auto-detect) raises
`SystemExit` from inside the meshtastic library when more than one serial
port candidate is present - uncaught by our `except Exception`, it
silently kills whatever thread called `connect()`, with no error ever
surfaced to the caller** ✅ FIXED (2026-08-23)

- Found live during real-hardware testing of Story 27.3's server GUI
  device dropdown (2026-08-23): selected "Auto-detect" from the
  dropdown, clicked Start Server, and the GUI sat on "Starting
  server..." indefinitely (2+ minutes, would never resolve) with the
  Start/Save/device controls stuck disabled. Looked like a hang; it
  wasn't - the background thread had already died almost instantly.
  `lsof` on the live process confirmed no serial file descriptor was
  ever opened, and `sample`'s thread listing showed nothing blocked in
  serial I/O - the thread was simply gone.
- **Root cause**, traced through the actual installed meshtastic
  library source (`meshtastic.serial_interface.SerialInterface.__init__`,
  `meshtastic.util.findPorts`/`our_exit`):
  ```python
  # meshtastic.serial_interface.SerialInterface.__init__, devPath=None:
  ports = meshtastic.util.findPorts(True)
  ...
  elif len(ports) > 1:
      message = "Warning: Multiple serial ports were detected so one "
                 "serial port must be specified with the '--port'.\n" ...
      meshtastic.util.our_exit(message)   # -> print(message); sys.exit(1)
  ```
  `sys.exit()` raises `SystemExit`, a `BaseException` subclass - NOT
  caught by `transport/meshtastic_serial.py`'s `connect()`, which only
  wraps the `SerialInterface(...)` constructor call in
  `except Exception as exc:`. `SystemExit` propagates straight past
  that handler, up through `btcmesh_server_gui.py`'s `run_server()`
  (whose own `except TransportConnectionError:` around the `connect()`
  call doesn't match it either), and terminates the background thread
  immediately - before it can ever push anything onto `result_queue`.
  With nothing ever arriving, the GUI has no way to know the attempt
  failed and stays showing "Starting server..." forever.
- **Reproduces whenever more than one serial candidate is attached** -
  not a rare edge case for this project's own real-hardware setup
  (Seeed + Heltec + Story 26.7 relay board routinely means 3+
  candidates), and Auto-detect is the spinner's *default* selection
  before any scan/explicit choice, so this is easy to hit by accident.
- **Not specific to the GUI or to Story 27.3** - any caller of
  `MeshtasticSerialTransport.connect(None)` with multiple candidates
  present hits this, including `btcmesh_server_cli.py`/
  `btcmesh_client_cli.py` if invoked without `-p`/`.env`'s
  `MESHTASTIC_SERIAL_PORT` set. Found via the server GUI simply because
  that's what was being tested at the time.
- **Fix** (branch `issue-41`): `connect()` in `transport/meshtastic_serial.py`
  now has a dedicated `except SystemExit as exc:` clause around the
  `SerialInterface(...)` constructor call, placed before the existing
  `except Exception`, converting it to
  `TransportConnectionError("Multiple Meshtastic devices detected - please
  select a specific device instead of Auto-detect")` - a normal,
  catchable connection failure instead of a silently killed thread.
- **Verified two ways**: a new regression test
  (`test_connect_raises_clear_error_on_system_exit` in
  `tests/test_meshtastic_serial_transport.py`, mocking
  `SerialInterface`'s side effect as `SystemExit(1)`); and live against
  the real installed meshtastic library with 5 actual serial candidates
  attached (Seeed, Heltec, relay board ports) - `transport.connect(None)`
  now returns the clean error instantly instead of hanging. Full suite
  813/813 passing.

## Server: "Automatic device-recovery enabled via relay" logs even when no relay is actually connected

**Issue 42: the startup log message claiming relay-based recovery is
"enabled" is based purely on `RELAY_SERIAL_PORT` being set in `.env` -
it never checks whether a relay board is actually plugged in and
responding** ✅ FIXED (2026-08-23)

- Found during real-hardware testing of Issue 41's fix: connected to
  the Seeed with the Story 26.7 relay board physically unplugged, but
  `RELAY_SERIAL_PORT` still set from earlier testing sessions. Server
  startup logged "Automatic device-recovery enabled via relay." anyway.
- **Root cause**: `core/device_watchdog.py`'s `build_device_watchdog()`
  sets `power_control = SerialRelayPowerControl(relay_port, ...)`
  purely from `get_relay_serial_port()` reading `.env` - `SerialRelayPowerControl.__init__`
  (`transport/power_control.py`) just stores the port/channel/baud
  strings, with no attempt to open or verify the port. The relay's
  serial port is only actually opened the first time `power_cycle()`
  runs - i.e. during a real recovery attempt, potentially much later
  (or never, if the device never actually wedges). So the message
  really means "a relay port is configured," not "a relay is present
  and working," but read like the latter.
- Also noted: the relay-board firmware
  (`hardware/power_relay_firmware/src/power_relay.ino`) only implements
  a `CYCLE` command - no lightweight PING/STATUS command exists to
  verify presence without actually cutting power, so an "actually
  verified" version of this message would need a firmware change too
  big for this fix.
- **Fix**: reworded the message (both `btcmesh_server_gui.py` and
  `btcmesh_server_cli.py`, which each log this independently) from "...
  enabled via relay." to "... configured via relay (RELAY_SERIAL_PORT
  set) - actual availability isn't confirmed until a recovery is
  attempted." - accurate about what's actually known at startup,
  without needing any new verification logic or firmware support.
- Full suite (812/812) passing after the wording change; corresponding
  tests in `tests/test_btcmesh_server_gui.py` and
  `tests/test_btcmesh_server_cli.py` updated to match.

## Server: Stop Server can take 60-90+ seconds if it coincides with a watchdog heartbeat check

**Issue 43: pressing Stop Server doesn't interrupt an in-flight
`DeviceWatchdog` heartbeat check/recovery cycle - if the click happens
to land while one is running, Stop can take well over a minute to
actually complete, and may log a "Device appears wedged" / "Device
recovered" cycle that looks alarming but is often just a transient,
self-resolving blip** 🔍 OPEN (informational - by-design tradeoff, not
a defect)

- Found during the same real-hardware session as Issue 42: pressed Stop
  Server while connected to the Seeed (no relay attached). The GUI
  logged "Device appears wedged - attempting automatic recovery..."
  then "Device recovered. Reconnected at ..." and only then "Server
  stopped." - over a minute after Stop was clicked.
- **Explained, not a bug**, via `server/run_loop.py`'s
  `run_polling_loop()` and `core/device_watchdog.py`:
  - The loop only re-checks `stop_check()` (`_stop_event.is_set`) at
    the *top* of each iteration - if it's currently inside
    `watchdog.tick(now)`, Stop has to wait for that call to return.
  - `tick()` only performs its (potentially slow) liveness check once
    every `heartbeat_interval_seconds` (60s) - so depending on timing,
    Stop can land anywhere from 0-60s before the next check even runs.
  - `check_alive()` (`transport/meshtastic_serial.py`) does a real
    round-trip admin request with the meshtastic library's own ~20s
    default timeout - a single slow/lost round-trip is enough to read
    as "not alive," which is a genuine live-hardware check, not a
    fabricated result.
  - If that trips `_recover()`, `_recover_once()` (`core/device_watchdog.py`)
    **always tries a plain disconnect+reconnect first, before ever
    considering the relay** (`_try_reconnect_without_power_cycle()`,
    with the comment "the device may have already come back on its
    own - power-cycling it again would just interrupt it needlessly").
    Since the Seeed was never actually wedged, this quick reconnect
    succeeded immediately and `power_control.power_cycle()` was never
    even called - **no relay involved at all**, contrary to how the
    log sequence might read.
- **Not the same failure mode as Issue 38** (Abort not interrupting a
  stuck chunk retry) even though the symptom-shape rhymes - this is a
  different control flow (`DeviceWatchdog.tick()`'s blocking
  `check_alive()` call), and fixing it would mean either making
  `check_alive()` interruptible mid-call or checking `stop_check()`
  from inside `tick()` itself - a real design change to a component
  whose whole contract is "runs on a single caller-controlled thread,
  can block up to ~20s" (see the class docstring).
- Not scoped or fixed here - logged so the (correct, expected, if
  alarming-looking) behavior is documented rather than mistaken for a
  bug on the next repeat sighting.
- **Real-world duration data point (2026-08-24)**: during the Issue 45
  incident, Stop Server was clicked right after a full main-hub
  disconnect/replug and took several minutes (well past the "60-90+
  seconds" estimate above) before finally showing "Server stopped." -
  confirmed via `sudo py-spy dump` mid-wait that the server thread was
  genuinely still working (not silently dead: the dump briefly missed
  it between samples, and a following one showed it inside the
  `check_alive()`/reconnect call path), and it did eventually complete
  correctly on its own, logging "Device recovered... on port
  /dev/cu.SLAB_USBtoUART" immediately before "Server stopped." A
  several-minute wait is plausible without any bug: the up-to-60s
  `heartbeat_interval_seconds` gap before `tick()` even re-checks,
  plus the ~20s `check_alive()` round trip, plus (if the device isn't
  immediately back) the `recovery_cooldown_seconds` (60s) between
  attempts, can chain across more than one cycle. Confirms this is the
  same accepted tradeoff described above, just a real number for how
  long the "if it coincides" case can actually run - the "60-90+
  seconds" framing above should be read as the common case, not an
  upper bound.
- **Update (Story 26.8, 2026-08-25)**: `check_alive()`'s timeout is now
  session-aware - short (~20s) while a transfer is actively in flight,
  but deliberately reverted back to long (~300s, matching this
  codebase's original pre-Issue-46 behavior) while idle, to avoid
  unnecessary recovery-cycle log noise from a single slow round-trip
  when nothing time-sensitive is happening. Issue 43's reproduction
  here was idle (no active session, no relay even attached), so the
  "60-90+ seconds" estimate above - written assuming the flat ~20s
  bound - now understates the idle case again: a Stop Server that
  coincides with an idle heartbeat check can take up to ~300s-class
  time, same order of magnitude as the pre-Issue-46 numbers this issue
  originally described. This is Story 26.8's own intended trade-off
  (see `project/plans/story_26_8.md`), not a new regression - the
  active-session case (the scenario Issue 46 actually needed fixed)
  stays fast.

## Test rig: unplugging one downstream USB hub can take down unrelated sibling devices on the same upstream hub

**Issue 45: physically unplugging the sub-hub carrying the Heltec +

  delivery - powering it did nothing because power was never the
  actual constraint.

  result, not a failure**:
  - **Server watchdog**: `check_alive()`'s heartbeat caught the dead
    connection, then `_try_reconnect_without_power_cycle()` genuinely
    reconnected once the hub came back, confirmed via a real matching

    already back by the time recovery ran), but a confirmed real
    disconnect→detect→reconnect cycle end-to-end.
  - **Server reassembly timeout**: correctly declared the in-flight
    session (14/15 chunks received) dead after `REASSEMBLY_TIMEOUT_SECONDS`
    and sent the accurate `BTC_NACK|...|Reassembly timeout` - the exact
    mechanism documented in Issue 40.
  - **Client send-timeout (Issue 21's fix)**: `transport.send()`'s
    10s worker-thread timeout fired correctly against the now-dead
    port, and the client's retry loop surfaced a specific, correct
    error ("Chunk 15: Send timed out after 10.0s - device may be
    unresponsive") and disconnected cleanly, instead of hanging.

## Server: `check_alive()` can block up to 5 minutes, not the ~20s its own docstring assumes

**Issue 46: `MeshtasticSerialTransport.check_alive()`'s `waitForAckNak()`
call inherits the meshtastic library's default 300-second reply
timeout, not the ~20s the method's own docstring documents - so a
single liveness check against a genuinely dead device can legitimately
block `DeviceWatchdog.tick()` for up to 5 minutes** ✅ FIXED (2026-08-24)

- Found 2026-08-24 while investigating why a server GUI screenshot
  showed no "Device appears wedged"/"Device recovered" messages in the
  Activity Log despite a real disconnect+reconnect having clearly
  happened (traced via the raw debug log). Added temporary diagnostic
  logging to every branch of `core/device_watchdog.py` (`record_failure()`,
  `tick()`, `_recover()`, `_recover_once()`, `_try_candidate()`, `_fail()`)
  printing to stderr (visible in the captured stdout log, unlike the
  GUI-only `result_queue` messages) and relaunched the server GUI to
  pick it up.
- **Root cause, confirmed via `sudo py-spy dump` mid-stall**: a fresh
  live reproduction (deliberate Heltec+relay hub unplug/replug) showed
  `tick() calling check_alive()` fire, then **nothing for over a
  minute** - `sudo py-spy dump --pid <server>` caught the exact frame:
  ```
  Thread-6 (run_server):
      waitForAckNak (meshtastic/util.py:226)
      waitForAckNak (meshtastic/mesh_interface.py:1030)
      check_alive (transport/meshtastic_serial.py:299)
      tick (core/device_watchdog.py:124)
  ```
  Checking `meshtastic.mesh_interface.MeshInterface.__init__`
  confirmed why: it defaults `timeout: int = 300` and builds
  `self._timeout = Timeout(maxSecs=timeout)` from it - the same
  `Timeout` object `waitForAckNak()` polls against. `MeshtasticSerialTransport.connect()`
  (`transport/meshtastic_serial.py`) constructs its `SerialInterface`
  without ever passing an explicit `timeout=`, so it silently inherits
  this 300-second cap. `check_alive()`'s own docstring claim ("~20s")
  was based on the bare `Timeout` class's own constructor default
  (`maxSecs: int=20`), not on how this codebase actually constructs
  the interface - the two never matched.
- **This explains two things already documented as separate findings
  tonight, retroactively**:
  - Issue 43's amendment (a real several-minute Stop Server wait) -
    not multiple chained heartbeat/cooldown cycles as guessed at the
    time, but potentially this *single* call legitimately running for
    up to 5 minutes.
  - The screenshot that started this investigation - the diagnostic
    trace from this same session **proved** `on_recovery_attempt()`
    and `on_recovered()` do fire correctly, in order, on the expected
    thread, with a real successful reconnect confirmed via matching
    `local_node_id`. There is no callback-wiring bug. The earlier
    screenshot simply caught a moment where `check_alive()` was still
    inside this same up-to-300s wait - the messages weren't lost, they
    just hadn't been generated yet.
- **Fixed** (PR #56, merged same day): `check_alive()` now builds its
  own short-lived `meshtastic.mesh_interface.Timeout(maxSecs=_CHECK_ALIVE_TIMEOUT_SECONDS)`
  (20.0s) and calls its `waitForAckNak()` directly against
  `self._iface._acknowledgment`, instead of delegating to
  `self._iface.waitForAckNak()` (which uses the interface's own
  300s-configured `Timeout`). Scoped to just this one probe - the
  interface's other reply-wait behavior (chunk-ack waits, config
  handshake, etc.) is untouched. New test
  `test_uses_its_own_short_timeout_not_the_interfaces_default` asserts
  the explicit `maxSecs` and that the interface's own `waitForAckNak()`
  is never called; 829/829 tests pass. A session-aware variant (short
  timeout only while a session is active, more lenient while idle, to
  avoid extra log noise during a prolonged genuine outage - the user's
  own suggestion) is intentionally left for a separate follow-up story
  rather than folded into this fix.
- The temporary `_diag()` diagnostic prints added to
  `core/device_watchdog.py` for this investigation were removed before
  the fix was committed - only the actual fix (in
  `transport/meshtastic_serial.py`) shipped.

## DeviceWatchdog: recovery-candidate scan never filters out the relay board's own control port

**Issue 48: `MeshtasticSerialTransport.scan_for_reconnect_candidates()`
returns every raw path from `scan_meshtastic_devices_detailed()`
unfiltered - including the Story 26.7 relay board's own control port -
so `DeviceWatchdog._try_candidate()` sends it a full Meshtastic protocol
handshake during every recovery cycle, corrupting the relay firmware's
serial read buffer and causing the very next `power_control.power_cycle()`
call to fail with `"ERR unknown command"`** ✅ FIXED (PR #59, 2026-08-24)

- Found 2026-08-24 during the first-ever real-hardware exercise of
  `DeviceWatchdog`'s actual `power_cycle()` path (never triggered live
  before this session - every prior real disconnect had been followed
  by a manual replug that let the plain reconnect-without-power-cycle
  path succeed first). Test setup: server GUI connected to the Seeed
  (deliberately reconfigured this session - the Seeed wedges more
  often than the Heltec, so it was made the server/relay-controlled
  device specifically to exercise this path; Heltec became the
  client's sending device). Seeed physically unplugged by hand and
  left unplugged (not replugged early, to avoid the short-circuit
  documented in the pending-tasks note this test was designed around).
  Diagnostic logging temporarily added to `core/device_watchdog.py`
  (same pattern as Issue 46) confirmed the full sequence live:
  `check_alive()` correctly timed out (~20s) -> `_recover_once()`
  disconnected -> `_try_reconnect_without_power_cycle()` correctly
  found nothing (Seeed genuinely absent) -> `power_control.power_cycle()`
  was called for the first time ever - and failed:
  `Relay board error: ERR unknown command`. Reproduced identically on
  a second, independent recovery cycle a minute later - not a fluke.
- **Root cause**: `core/device_watchdog.py`'s `_try_candidate()` calls
  `self._transport.connect(path)` on every path
  `scan_for_reconnect_candidates()` returns, with no relay-awareness at
  all (by design - `DeviceWatchdog` is deliberately transport-agnostic,
  see its module docstring). But
  `transport/meshtastic_serial.py:324`'s `scan_for_reconnect_candidates()`
  just returns `[d.path for d in scan_meshtastic_devices_detailed()]` -
  every raw candidate, unfiltered. Live server-log evidence during
  recovery showed the transport actually opening a Meshtastic
  connection (`want_config_id`, full binary framing) against
  `/dev/cu.usbserial-112440`/`/dev/cu.wchusbserial112440` - the relay
  board's own two OS-level aliases, not a Meshtastic device at all.
  That handshake's binary garbage left sitting in (or colliding with)
  the relay firmware's serial buffer explains why the very next,
  separate `SerialRelayPowerControl.power_cycle()` connection - opened
  moments later to send a clean `CYCLE 1 15\n` - had its first line
  read back corrupted, tripping `power_relay.ino`'s
  `line.substring(0, firstSpace) != "CYCLE"` check
  (`hardware/power_relay_firmware/src/power_relay.ino:117-119`).
- **This is a missed sixth call site of a pattern Issue 37 already
  fixed everywhere else it was known to exist.** Issue 37's
  false-positive-candidate fix added a `probe_relay_board_id()` guard
  (safe, ~2s-timeout, protocol-level positive identification - never a
  guess) in front of five direct `transport.connect()` call sites:
  the client's `on_device_selected()`, `on_refresh_nodes()`,
  `_connect_with_retry()` (Send), and the server/CLI's
  `on_start_pressed()`/`run_server()`. `DeviceWatchdog._try_candidate()`
  is functionally a sixth such call site (added later, by Story 26.4,
  before Issue 37's audit existed) that was never covered - it does
  its own direct `transport.connect(path)` with no guard at all.
- **Practical impact**: any real deployment combining the Story 26.7
  relay board with `DeviceWatchdog` hits this on *every* recovery
  cycle that reaches `power_cycle()` - not an edge case. The
  recovery-without-power-cycle path is unaffected (it only needs a
  *successful* connect to the real device, and the relay board
  correctly fails that with `TransportConnectionError` rather than a
  false match) - the damage is specifically to the relay's own serial
  state, breaking the *next* legitimate `power_cycle()` call.
- **Fixed**: `scan_for_reconnect_candidates()` (`transport/meshtastic_serial.py`)
  now filters at the same layer Issue 37 already established - reuses
  `probe_relay_board_id()` (already lives in `transport/power_control.py`,
  already proven safe against real Meshtastic devices during Issue 37's
  live verification) to exclude any candidate path that identifies as
  the relay board, before returning the list to `DeviceWatchdog`. Keeps
  `DeviceWatchdog` itself untouched/transport-agnostic - the filter
  lives in the Meshtastic-specific transport, exactly where the raw
  candidate list is produced. Accepted tradeoff: adds up to ~2s of
  probe latency per non-relay candidate per scan pass (worst case for a
  real device that doesn't answer the relay's `ID` probe) - repeated on
  each `_wait_for_device()` backoff iteration, but small relative to
  its 60s total window. New regression test
  `test_excludes_relay_board_port` in
  `tests/test_meshtastic_serial_transport.py`. 847/847 tests pass.
- **Verified end-to-end on real hardware (2026-08-24)**, same rig as
  the original repro: `power_cycle()` succeeded cleanly 4/4 times after
  the fix (vs. failing every time before it). One full recovery cycle
  completed start to finish - disconnect -> failed no-power-cycle scan
  (device genuinely absent) -> real `power_cycle()` -> device
  reappears -> identity-matched reconnect via `_wait_for_device()` -
  the first time `DeviceWatchdog`'s actual power-cycle recovery path
  has ever been exercised live, not just unit-tested. This also
  resolves Story 28.3's previously-stale `[ ]` status in
  `project/tasks.txt` (see that story's notes).

**Issue 50: `MeshCoreSerialTransport._subscribe()` never actually delivers
incoming messages - it subscribes to `CONTACT_MSG_RECV` directly, but
that event only ever fires as the reply to an explicit pull the
transport never makes** ✅ FIXED (2026-08-27)

- Found 2026-08-26, during the first-ever real-hardware MeshCore↔MeshCore
  test (two freshly-flashed devices for Epic 9: a Heltec Vision Master
  T190 as client, a Heltec V3 as server - see `project/plans/story_30_1.md`
  and `project/plans/story_30_2.md` for the transport/validation work this
  hardware finally exercises for real).
- **Root cause**: MeshCore's companion protocol does not push received
  messages to the client proactively. When a message arrives, the
  firmware buffers it and sends a lightweight `MESSAGES_WAITING`
  notification only; the companion client is expected to then actively
  pull the message via `CMD_SYNC_NEXT_MESSAGE` (`commands.get_msg()` in
  `meshcore_py`). Only the *reply* to that pull is what `meshcore_py`'s
  `reader.py` parses into a `CONTACT_MSG_RECV` event - confirmed directly
  in the library source, where `PacketType.CONTACT_MSG_RECV_V3` is
  commented "A reply to CMD_SYNC_NEXT_MESSAGE (ver >= 3)".
  `MeshCoreSerialTransport._subscribe()` (`transport/meshcore_serial.py`)
  subscribes only to `EventType.CONTACT_MSG_RECV` and never calls
  `get_msg()` (or `meshcore_py`'s own `start_auto_message_fetching()`
  helper, which does exactly this pull automatically) - so
  `CONTACT_MSG_RECV` never fires for a real incoming message, and the
  handler registered via `set_message_handler()` is never invoked, even
  though the message physically reached the radio.
- **Confirmed via real hardware**: sent a plain test message
  (`commands.send_msg()`) from one flashed device directly to the other.
  The receiving device's raw event stream (subscribed to every
  `EventType`, not just the one BTCMesh listens for) showed a genuine
  `RX_LOG_DATA` event (SNR 11.75, RSSI -6, `route_typename: DIRECT`,
  `payload_typename: TEXT_MSG`) immediately followed by
  `MESSAGES_WAITING` - but `CONTACT_MSG_RECV` never fired, because
  nothing ever called the pull that produces it.
- **Why the mocked unit test suite never caught this**:
  `tests/test_meshcore_serial_transport.py` mocks `sys.modules['meshcore']`
  entirely; its receive tests simulate delivery by directly invoking the
  registered `_on_event` callback, never modeling the real
  `MESSAGES_WAITING` → `get_msg()` → `CONTACT_MSG_RECV` round trip. The
  gap is invisible to a mocked test by construction - only real hardware
  (or a much more faithful mock) can surface it. This is exactly the risk
  `project/plans/story_30_1.md` flagged Story 30.5 ("real-hardware
  verification script") as existing to catch.
- **Fix**: `_subscribe()` now also calls `await
  self._mc.start_auto_message_fetching()` alongside its existing
  `EventType.CONTACT_MSG_RECV` subscription (that event is still what the
  fetched-message reply arrives as - the missing piece was the "go get it"
  trigger), bridged through the class's existing `_run_coro()` sync/async
  bridge - the same pattern `connect()`/`send()`/`check_alive()` already
  use. `_unsubscribe()` symmetrically calls `stop_auto_message_fetching()`.
- **Confirmed via real hardware**: on first connect after the fix, the
  server immediately drained a message that had been stuck in the
  device's queue since the original diagnosis session - direct proof
  `get_msg()` is now actually being called. A live send/receive round
  trip then produced a real `BTC_CHUNK_ACK` delivered back to the client
  (`Received ACK for chunk 1/3`) - the first genuine bidirectional
  message exchange over MeshCore hardware in this project. (Chunk 2 of
  that same test was lost to a separate, newly-found timing issue - see
  [[Issue 52]] - unrelated to this fix; Issue 50 itself, "does a message
  ever reach the handler at all," is conclusively resolved.)
- Related: [[Issue 51]] (fixed alongside it - independent root causes,
  independent branches/PRs, per existing practice in this repo) and
  [[Issue 52]] (a new, separate finding surfaced while verifying this fix).

**Issue 51: `core/constants.py`'s `DEFAULT_CHUNK_SIZE` (170, tuned for
Meshtastic) exceeds MeshCore's hard per-message cap, so every `BTC_TX`
chunk is rejected outright over MeshCore** ✅ FIXED (2026-08-27)

- Found 2026-08-26, alongside Issue 50, during the first real-hardware
  MeshCore↔MeshCore test.
- **Root cause**: `DEFAULT_CHUNK_SIZE=170` was sized against Meshtastic's
  LongFast airtime budget (per its own docstring in
  `core/constants.py`) - `project/plans/story_30_1.md`'s Critical Files
  table already flagged this value as needing "re-validation against
  MeshCore's framing in a later story, not blocking this one." MeshCore's
  companion firmware hard-caps a single text message payload at
  `MAX_TEXT_LEN = 10*CIPHER_BLOCK_SIZE = 160` bytes
  (`src/helpers/BaseChatMesh.h`, `CIPHER_BLOCK_SIZE=16` in
  `src/MeshCore.h`, both in the `meshcore-dev/MeshCore` firmware repo).
  BTCMesh's wire format adds `BTC_TX|<5-char session>|<n>/<total>|`
  framing (~17-19 bytes) on top of the 170-char hex payload, landing
  around 187-189 bytes total - over MeshCore's 160-byte ceiling.
  `Mesh::createDatagram()` rejects any text longer than `MAX_TEXT_LEN`
  outright (`composeMsgPacket()` in `BaseChatMesh.cpp` returns NULL before
  ever reaching the radio), which the companion protocol reports back as
  `MSG_SEND_FAILED` → `ERR_CODE_TABLE_FULL` - a generic "packet could not
  be created" code reused across several unrelated failure paths in
  `examples/companion_radio/MyMesh.cpp`, not a literal contact-table or
  packet-pool exhaustion (initially misleading during diagnosis - traced
  through the actual firmware source rather than assumed from the error
  name).
- **Confirmed via real hardware**: every attempt at the default 170-char
  chunk size failed immediately on chunk 1/5 with `{'error_code': 3,
  'code_string': 'ERR_CODE_TABLE_FULL'}`. Dropping to a 100-char chunk
  size (117-byte wire message, well under the 160-byte cap) sent
  successfully with no send-side error at all - isolating the cause to
  message length, not a hardware or radio problem.
- **Fix**: added a transport-aware `max_chunk_size` abstract property to
  `BaseTransport` - same shape as Story 30.2's `validate_destination()`.
  `MeshtasticSerialTransport.max_chunk_size` returns the existing
  `DEFAULT_CHUNK_SIZE` (170, no behavior change);
  `MeshCoreSerialTransport.max_chunk_size` returns a new
  `MESHCORE_MAX_CHUNK_SIZE = 120` (`core/constants.py`) - safely under the
  160-byte `MAX_TEXT_LEN` ceiling with real margin below the theoretical
  141-byte edge, per [[feedback_ground_caps_in_physical_constraints]].
  `client/sender.py::TransactionSender.send_transaction()` now chunks via
  `self.transport.max_chunk_size` instead of the hardcoded default;
  `create_preview()` (used by both the CLI's `--dry-run` and the GUI's
  preview button) takes an optional `chunk_size` parameter, defaulting to
  `DEFAULT_CHUNK_SIZE` so the Meshtastic-only GUI needed zero changes.
  `btcmesh_client_cli.py`'s dry-run path now resolves the selected
  transport's cap before previewing. **Confirmed via real hardware**:
  re-ran the exact send that previously failed immediately with
  `ERR_CODE_TABLE_FULL` - it now sends every chunk cleanly at the new
  default size, retrying only on ACK timeout (Issue 50's separate bug,
  since fixed), never on the send itself.
- Related: [[Issue 50]] (fixed).

**Issue 52: `_on_event` deadlocks against its own transport when the
receive handler sends - misdiagnosed at first as a MeshCore routing
delay** ✅ FIXED (2026-08-28)

- Found 2026-08-27, verifying the [[Issue 50]] fix on real hardware: a
  clean 3-chunk send got a real `BTC_CHUNK_ACK` back for chunk 1 - proving
  Issue 50's fix works - but the ACK took roughly 20 seconds to arrive.
  The server's own log showed why: `Error from <sender>: Send timed out
  after 10.0s - device may be unresponsive` when it first tried to send
  the ACK back, followed by an apparently-successful retry. By the time
  chunk 2 was sent, too much of the reassembly window had elapsed; the
  server's 30-second reassembly timeout (`core/config_loader.py::load_reassembly_timeout()`'s
  own default - notably a different literal, 30, than
  `core/constants.py::DEFAULT_REASSEMBLY_TIMEOUT`'s 300; the two aren't
  the same constant despite the similar name) fired having only received
  1 of 3 chunks, and the session was discarded with a NACK.
- **Initial hypothesis was wrong, and disproven by direct measurement**:
  the write-up above guessed flood-routing cost as the "likely root
  cause." A standalone `commands.send_msg()` call (with or without the
  auto-fetch loop active) measured under 0.1s, even though the contacts'
  cached path was already direct (`out_path_len=0`, not
  `OUT_PATH_UNKNOWN`) - flood-routing was never the bottleneck.
- **Confirmed root cause**: `MeshCoreSerialTransport._subscribe()`'s
  `_on_event` callback runs on the transport's own background asyncio
  loop thread (`self._loop`/`self._loop_thread`, from `_ensure_loop()`)
  and called `self._handler(text, sender)` synchronously, inline. In real
  usage that handler is `TransactionReceiver._on_message`
  (`server/receiver.py`), which - to send a chunk ACK - calls
  `self.transport.send(...)`. `send()` bridges through `_run_coro()`,
  which does `asyncio.run_coroutine_threadsafe(coro, self._loop).result(timeout=...)` -
  scheduling new work onto `self._loop` and blocking the *calling* thread
  until it completes. The calling thread here *is* `self._loop_thread`
  itself (already inside the synchronous `self._handler()` call, invoked
  from `_on_event`, running on that same loop) - it can never get back
  around to running the coroutine it just scheduled, because it's blocked
  waiting on a result only it can produce. Reproduced directly (not
  inferred): a handler that calls `transport.send()` on the same
  transport instance took exactly `_SEND_TIMEOUT_SECONDS` (10.00s) before
  raising `TransportSendError`, every time, independent of routing/path
  state - a same-thread reentrancy deadlock, not a network delay. Also
  explains why `MeshtasticSerialTransport` never had this problem - its
  `send()` spins up a fresh worker thread per call (Issue 21) rather than
  sharing one loop thread for every bridged operation, so its receive
  callback can never contend with a `send()` call this way.
- **Fix**: `_on_event` no longer calls the handler inline. A single
  dedicated dispatch thread, fed by a queue and started alongside the
  `CONTACT_MSG_RECV` subscription, now invokes the handler; `_on_event`
  itself just enqueues `(text, sender)` and returns immediately, freeing
  the loop thread to actually run whatever the handler schedules via
  `_run_coro()`. One worker thread (rather than one thread per message)
  keeps handling serialized, matching this protocol's stop-and-wait
  shape. Checked prior art first: `meshcore-cli` and the community
  `meshcore-mqtt` bridge (the closest published analog to this
  transport) both avoid this class of bug, but only because both are
  pure `async def` applications with no sync/async bridge at all -
  `meshcore-mqtt` does apply the same "decouple receive from handling"
  principle via an `asyncio.Queue`, which is what this fix's queue design
  borrows, even though its own fully-async architecture never needed the
  thread-bridging `BaseTransport`'s synchronous contract requires here.
- **Confirmed via real hardware**: the exact reproduction above now
  returns in ~0.01s instead of a guaranteed 10.00s hang. A full 3-chunk
  send/receive round trip then completed end-to-end for the first time -
  all three chunks sent, ACKed, and reassembled server-side, ending in
  the server's real, specific validation NACK (`"Invalid transaction
  structure"`, correctly rejecting the test placeholder hex) rather than
  the generic `"Internal server error"` catch-all from before.
- **Also affects the server's outgoing ACK, not just client sends, and
  mislabels the failure when it does**: found 2026-08-27 in a follow-up
  real-hardware run. A single-chunk transaction reassembled successfully
  server-side (`server/receiver.py`'s `_on_message` logged "Reassembly
  successful" instantly), but the client's final result was `Transaction
  failed: Internal server error` - not the RPC-specific NACK that
  scenario actually has (`_broadcast()`, `server/receiver.py:298`, sends
  the clear, dedicated `"Bitcoin RPC not connected"` NACK when
  `rpc_client is None`, confirmed by reading that code path directly).
  The server's own log explains why: sending the per-chunk
  `BTC_CHUNK_ACK` back (`self._send(ack, sender_id)`, `server/receiver.py:228`)
  hit the same `_SEND_TIMEOUT_SECONDS` timeout this issue is about,
  raising `TransportSendError` *before* the RPC-connection check was ever
  reached. That exception isn't caught locally - it falls through to
  `_on_message`'s generic `except Exception` catch-all
  (`server/receiver.py:254-261`), which sends the client a NACK reading
  `"Internal server error"` instead of anything indicating a transport
  timeout. The chunk ACK apparently still went out shortly after
  (`MeshCoreSerialTransport.send()`'s bridge abandons the wait but can't
  cancel the underlying coroutine - same "abandoned, not killed" shape as
  `MeshtasticSerialTransport.send()`'s Issue 21 fix - the client did
  receive `BTC_CHUNK_ACK` a moment later), but by then the server-side
  code had already moved on to the generic-error branch. Now that the
  deadlock that triggered this specific timeout is fixed, this exact
  scenario shouldn't recur - but `_on_message`'s generic catch-all itself
  (`server/receiver.py:254-261`) still folds *any* unexpected exception
  into the same opaque `"Internal server error"` string, for any future
  cause. Left as-is here (out of scope for this fix, which only touched
  `transport/meshcore_serial.py`) - worth a small follow-up in
  `server/receiver.py` if it's ever worth the churn, not urgent enough to
  warrant its own tracked issue on its own.
- Related: [[Issue 50]].

**Issue 53: `disconnect()` has no timeout guard, unlike `send()` (Issue 21) -
Server GUI's Stop Server hung indefinitely on real hardware, stuck printing
the `meshtastic` library's own "Waiting for free space in TX Queue" debug
line** ✅ FIXED

- Observed 2026-08-28 during Story 30.4's manual GUI verification: server
  GUI connected fine to a real Meshtastic device (default transport,
  unrelated to Story 30.4's new selector), then Stop Server was pressed.
  The process hung, repeatedly printing `[DEBUG] Waiting for free space in
  TX Queue` to the terminal with no end in sight - required a manual
  Ctrl+C to recover.
- **Confirmed not a Story 30.4 regression**: `MeshtasticSerialTransport.disconnect()`
  (`transport/meshtastic_serial.py:180-196`) is untouched by this story -
  the only change anywhere near it was swapping a direct
  `MeshtasticSerialTransport()` construction for
  `get_transport("meshtastic")`, which returns the exact same class
  instance via `transport/factory.py`. Confirmed by reading the method
  directly, not inferred.
- **Where it's actually stuck**: `disconnect()` calls `self._iface.close()`
  (the `meshtastic` PyPI library's own interface object), wrapped in a
  bare `try/except Exception: pass` - which only guards against `close()`
  *raising*, not against it *hanging*. The observed debug line comes from
  inside the library itself, suggesting `close()` is internally trying to
  flush a backed-up outgoing packet queue on the physical device before
  it will return, with no timeout of its own either.
- **Same class of bug as Issue 21**, just on the opposite end of the
  connection lifecycle: Issue 21 found `send()` had no bound and fixed it
  with a dedicated bounded worker thread. `disconnect()`/`close()` still
  has no equivalent bound anywhere in `BaseTransport`'s contract or either
  concrete transport - a device with a stuck/backed-up queue at
  disconnect time can hang the caller (GUI or CLI) exactly the way
  `send()` used to.
- **Fix**: `MeshtasticSerialTransport.disconnect()` now runs
  `iface.close()` on a daemon worker thread and
  `join(timeout=_SEND_TIMEOUT_SECONDS)`s it, mirroring `send()`'s Issue
  21 fix exactly - but on timeout, `disconnect()` logs a warning and
  continues rather than raising. `send()` raises because callers expect
  to handle a failed send; `disconnect()` never raises anywhere today,
  confirmed by auditing every real call site (`core/device_watchdog.py`'s
  `_recover_once()` calls it mid-recovery with zero exception handling;
  every GUI/CLI call site calls it unguarded, several in a `finally`
  block) - none of them are prepared to catch an exception from it, and
  `disconnect()`'s own docstring already promises "safe to call". On
  timeout the underlying library connection is abandoned (leaked), the
  same way `send()`'s worker thread is abandoned - Python has no API to
  forcibly stop a thread.
- **`MeshCoreSerialTransport.disconnect()`**: its `_mc.disconnect()` call
  was already bounded via `_run_coro()`'s `future.result(timeout=...)`,
  and reading `_ensure_loop()` confirmed `self._loop.stop()` (scheduled
  via `call_soon_threadsafe`, which wakes the loop's selector) reliably
  makes `run_forever()` return even with the just-abandoned
  `_mc.disconnect()` coroutine still pending - so this transport was
  never actually exposed to the observed hang. Found one real gap while
  verifying that, though: `self._loop.close()` was called unconditionally
  after the loop-thread `join()`, which raises `RuntimeError: Cannot
  close a running event loop` if that join ever genuinely timed out (a
  low-probability race, not the bug observed here, but a real violation
  of "never raises" all the same) - now guarded: `close()` is skipped
  (with a warning logged) whenever the loop thread is still alive after
  its bounded join.
- Real-hardware repro of the *exact* observed hang wasn't attempted -
  unlike Issue 21's dedicated relay-power-cut script
  (`send_timeout_test.py`), there's no equivalent way to force a backed-up
  TX queue on demand. Verified instead: the full unit test suite (944
  tests, including new timeout-simulation tests for both transports
  mirroring `send()`'s existing `test_send_raises_timeout_error_when_*_blocks`
  pattern) stays green, and a real Start Server → Stop Server smoke check
  on real hardware (Meshtastic device, `!7c5b4418`) confirmed no
  regression - `disconnect()` completed cleanly and immediately.
- **A different real hang surfaced during that same smoke check, at
  first looking like a possible regression**: a couple of runs appeared
  to hang after clicking Stop. Caught directly with `sample` (see Issue
  56) - it was a background device-identity-probe thread stuck in the
  OS's own `open()` syscall trying to open a candidate serial port,
  unrelated to this fix. The main thread's own sample at that same
  moment showed normal, responsive Kivy activity, and a subsequent Stop
  Server on a fresh instance completed immediately with no code changes -
  confirming this fix is not the cause. Logged separately as Issue 56
  rather than folded in here, since it's a different call site
  (`connect()`'s port-open step, not `disconnect()`).

**Issue 55: MeshCore relay is noticeably slower than the equivalent
Meshtastic relay - not yet root-caused** Open

- Raised 2026-08-28, right after Story 30.4's real-hardware GUI
  verification: a chunked send that completed via the GUI felt
  "extremely slow" compared to how Meshtastic relays have felt in this
  same environment.
- **Not a Story 30.4 regression**: this story only added transport
  selection UI, device scanning, and identity probing - it made no
  changes anywhere in the actual send/receive/dispatch path
  (`transport/meshcore_serial.py`'s `send()`/`_on_event()`/dispatch
  thread, untouched here).
- **Two known, already-documented contributors, neither fully
  investigated as the actual explanation**:
  1. MeshCore's `MESHCORE_MAX_CHUNK_SIZE` is 120 vs Meshtastic's
     `DEFAULT_CHUNK_SIZE` 170 (Issue 51 - MeshCore's own protocol enforces
     a stricter ~160-byte total message cap) - the same transaction needs
     more chunks, hence more round trips, over MeshCore.
  2. Real hardware runs earlier in this session (Story 30.5's
     verification, and this story's own GUI testing) already showed
     individual chunks frequently needing a second send attempt before
     ACKing - each retry costs a full `_SEND_TIMEOUT_SECONDS` (10s) wait,
     and a multi-chunk transaction with several such retries adds up
     quickly (one logged run took ~2.5 minutes for 6 chunks; a different
     run of the same script completed in ~12s with zero retries - real,
     substantial run-to-run variability on the same hardware).
- Not root-caused further here - logged for a future investigation into
  *why* individual chunk sends need retries this often on MeshCore
  specifically (radio config - `radio_sf`/`radio_bw`/`radio_freq` are all
  present in `self_info` and not yet compared against Meshtastic's
  defaults on the same boards; duty-cycle/airtime limits; MeshCore's own
  path-routing behavior) rather than just accepting the retry-and-wait
  behavior as a given.

**Issue 56: `connect()` has no timeout on its port-open step - can hang
the primary Start Server flow, not just the background device scan - a
third occurrence of Issues 21/53's "unbounded blocking call" pattern**
✅ FIXED

- Found 2026-08-29 while doing the real-hardware smoke check for Issue
  53's fix: the server GUI's Stop Server appeared to hang on a couple of
  runs, closely enough after Issue 53's fix to look like a regression at
  first. Caught directly with macOS's `sample` tool (no `py-spy`/`sudo`
  needed for a process the current user owns) while genuinely reproduced:
  `Thread_8766651: Thread-2 (probe_thread)` showed 264/264 samples over a
  3-second window all sitting in the exact same raw syscall stack:
  `os_open` (Python) → `open` → `__open` (`libsystem_kernel.dylib`) -
  i.e. still blocked in the kernel's own `open()` call, not anywhere in
  Python/BTCMesh code at all.
- **Confirmed not Issue 53**: the main thread's own sample, taken at the
  same moment, showed completely normal Kivy rendering/event-loop
  activity (`SDL_WaitEventTimeout_REAL`, GL drawing) - not stuck. A
  subsequent Stop Server on a fresh instance completed immediately, with
  no change to the code, confirming Issue 53's fix itself is sound; this
  is a separate, pre-existing bug that happened to be visible at the same
  time.
- **Reproduced a second time, independently, same result**: on another
  fresh instance, the device scan launched on startup never finished
  ("Identifying devices..." stayed up indefinitely - user-observed as
  "endlessly scanning"). Sampled again: 1449/1449 samples over the
  window, same thread, same exact stack (`Thread-2 (probe_thread)` →
  `os_open` → `__open`). Meanwhile the *rest* of the app kept working
  normally in the same run (a separate connect/disconnect cycle for
  Start Server completed and logged normally) - confirming this one
  specific background probe thread is what's genuinely stuck, silently,
  while everything else keeps working; the user-visible symptom is just
  that the scan's busy indicator never clears.
- **Where**: `"Thread-2 (probe_thread)"` is the inner closure inside
  `gui/gui_common.py`'s `probe_devices_in_background()` - the background
  device-identity scan both GUIs run after finding multiple candidate
  ports (`probe_device_identity()` in `core/meshtastic_utils.py`/
  `core/meshcore_utils.py`). Somewhere under `transport.connect(path)`
  for one of the scanned candidates, the underlying serial library's
  `open()` call on that port never returns.
- **Worse than "one candidate stays unresolved"**: user-confirmed on the
  second repro - *none* of the scanned devices got identity labels, not
  just the stuck one. `probe_devices_in_background()`'s probe loop
  (`for device in list(devices): ... identity = probe_device_identity(...)`)
  is strictly sequential and has no per-candidate bound - one candidate
  stuck in `open()` blocks every candidate after it in the same batch
  from ever being probed, silently, with no error/warning surfaced. In
  practice this can mean the entire device dropdown stays unlabeled raw
  paths indefinitely, not just a single missing entry.
- **Third reproduction - confirmed on the primary Start Server flow
  itself, not just the background scan**: same session, user selected a
  candidate device (Seeed-VID) and pressed Start Server; both the scan
  *and* Start Server appeared stuck at the same time. Sampled again:
  `Thread-3 (run_server)` - `btcmesh_server_gui.py`'s
  `on_start_pressed()`'s own server thread, a completely different call
  site than the scan's `probe_thread` - showed 1572/1572 samples in the
  identical stack (`os_open` → `open` → `__open`). This confirms the real
  severity: it's not only a background-scan cosmetic issue, `connect()`'s
  missing timeout can hang the actual primary workflow (Start Server)
  exactly the way Issue 21's missing `send()` timeout used to hang Send -
  raising this to Major.
- **Same class of bug as Issues 21 and 53, one level down**: `send()` had
  no bound on the underlying library call (Issue 21, fixed); `disconnect()`
  had no bound on `iface.close()` (Issue 53, fixed); `connect()` has no
  bound on the initial port-`open()` step either - all three are the same
  "an OS/library call can block forever, and nothing here stops it"
  pattern applied to a third call site.
- Not root-caused further (exactly which candidate port, or why that
  specific `open()` blocks, wasn't isolated - lsof at the time showed
  nothing else on this machine holding that port, so simple lock
  contention from another process doesn't obviously explain it) - the
  underlying *why some devices wedge* remains an open hardware/driver
  question (matching this project's other documented device-wedge
  issues), but the missing-timeout bug itself is fixed below.
- **Fix**: `MeshtasticSerialTransport.connect()`'s
  `SerialInterface(connectNow=False)` construction now runs on a daemon
  worker thread with a hard `join(timeout=_CONNECT_TIMEOUT_SECONDS)`
  (20.0s - matching `_CHECK_ALIVE_TIMEOUT_SECONDS`'s existing precedent
  in this file), mirroring `send()`'s Issue 21 fix exactly. Unlike
  `disconnect()`'s Issue 53 fix, `connect()` already has a "raises on any
  failure" contract every real caller expects, so a timeout raises
  `TransportConnectionError` here rather than swallowing. The existing
  `SystemExit` (Issue 41)/`NoDeviceError`/generic-exception dispatch is
  preserved exactly, just moved to run after the worker thread completes.
  Confirmed via git history (`git log -S`) that the vulnerable code
  hasn't changed since commit `533eb49`, well before Issue 21 and
  everything from this epic - not a regression, just newly exposed by
  more real devices being connected simultaneously during this session's
  testing than usual.
- **`MeshCoreSerialTransport.connect()` deliberately not touched**: it
  already wraps its equivalent `create_serial()` step in
  `_run_coro(_do_connect(), self._CONNECT_TIMEOUT_SECONDS)` -
  `future.result(timeout=...)` already bounds the *calling* thread's
  wait, so a caller already gets a timely `TransportConnectionError`
  rather than hanging, which is what was actually observed and confirmed
  here (only ever on the Meshtastic path, never MeshCore). One smaller,
  unconfirmed caveat noted for the record: if `create_serial()` does a
  blocking (non-async) `open()` internally on the loop's own background
  thread, that specific transport *instance*'s loop thread could stay
  stuck forever afterward even though the caller recovers correctly -
  every real caller constructs a fresh instance per attempt, so this
  doesn't compound into a growing problem today, and speculatively
  changing unconfirmed code wasn't warranted.
- Verified: full unit test suite (942 tests, including a new
  `test_connect_raises_timeout_error_when_port_open_blocks` mirroring
  `send()`'s existing timeout-test pattern) passes. Real-hardware
  confirmation against the actual wedged Seeed device from this session
  (the same device the bug was caught on) is the next step, still to be
  done live.
